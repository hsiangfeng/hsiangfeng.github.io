Zeabur 結束營運：台灣新創的跌倒與成長

前言

這陣子看到 Zeabur 宣布結束營運，覺得滿惋惜的，所以就寫一篇文章聊聊自己跟 Zeabur 的一些機緣，順便記錄一下自己的想法，當作回顧。

Zeabur 停止營運公告

先說在前面，我跟 Zeabur 的創辦人是朋友，可是我同時也是八月那次資安事件的受害者之一（API Key 被盜刷了 500 多美金），所以這篇文章會同時帶著這兩個身分來聊。

與 Zeabur 的相遇

其實我跟 Zeabur 創辦人 Yuanlin 大約是在 2023 年認識的（看 Discord 最後紀錄），至於實際上怎麼認識的，老實講我也忘了。

那時候剛好遇到 Heroku 宣佈 2022/11/28 起停止免費方案，我正在找替代方案來放一些小型的 MVP 專案，當時評估的是 Render.com 跟 Fly.io 這兩個平台，過了一段時間後，就偶然認識了正在推廣 Zeabur 的 Yuanlin。

然後就...對，不明原因成為了朋友 xD

那段時間 Zeabur 主打的就是大家所熟悉的「簡單、快速、方便」，你幾乎可以「一鍵」就部署自己的專案，減少過多繁瑣的步驟，讓你可以專注在開發上，而不用花一堆時間研究部署。

早期呢...其實滿多細節我都有幫忙抓，像是教學文件的配色問題：

Zeabur 教學文件

也因為當時還在早期，文件比較不齊全，所以我也給了一些方向上的建議，像是可以先列出主流框架的文件就好：

Zeabur 教學文件

大致上就是這樣，算是初步聊一下自己跟 Zeabur 的相遇故事，也算是很早期的使用者之一了吧（笑）。

協助推廣 Zeabur

後來跟 Yuanlin 聊過好幾次之後，我其實感覺得到他是真心想解決開發者在部署上的痛點，想讓 Zeabur 成為一個真正能幫助開發者的工具。

但不得不說這條路很難走，畢竟 PaaS 這個市場已經有很多競爭者，像是 Render、Fly.io、Vercel 等等，每一個都是很強大的對手，那該怎麼走出自己獨一無二的路呢？這真的是一大考驗跟難題。

當市場上都有類似的產品時，你該怎麼說服我使用你的產品？

我覺得當時 Yuanlin 其實有在思考這件事，也嘗試了一些不同的方式，像是透過社群、部落格、教學文件等等，讓更多人知道 Zeabur 的存在，而以當時來講，最好的切入點莫過於「亞洲地區的開發者」吧。

畢竟，儘管開發者看英文是常態，但如果有一個平台能讓你不用看英文文件就快速部署自己的專案，對華語圈的開發者來講真的很方便 xD

基於這些零零碎碎的過程與溝通，我選擇相信 Yuanlin，並開始幫忙寫一些文章推廣 Zeabur，像是 除了 Render 與 Fly 之外，你還可以考慮 Zeabur 服務（2023/04/01）、Day24-部署到 Zeabur（2023/10/08）。

雖然我不知道我的協助有多少成效就是了。

後來，因為我待的公司是教育單位，會接觸到許多學生，當時開課也很煩惱學生在部署上遇到的問題，像是 Heroku 停止免費方案後，學生就沒有地方可以部署自己的專案，所以就想說推薦給公司，讓公司認識一下 Zeabur，看能不能成為教材的一部分，但一開始是被拒絕的，畢竟要推任何一個平台都需要經過評估，我認為這也很合理。

所以取而代之就是...讓我凹一下 Yuanlin 來擔任講者或當客服，這樣他還可以趁機會業配一下 XD

一路走來，真的一帆風順嗎？

老實講，我覺得一直都不是很順利，如同前面所說，市場上本來就有許多 PaaS 平台，當開發者都已經習慣既有的平台時，你沒事也不會想跳槽吧？畢竟遷移主機、遷移資料庫、遷移專案等等，都是要花時間跟成本的事情，所以要說服開發者改用 Zeabur 真的不容易。

後來大約 2024～2025 年，AI 開始快速崛起，像是 ChatGPT、Gemini、Claude 等等，我相信 Zeabur 也是從這時候開始思考怎麼讓 AI 跟 Zeabur 結合，畢竟純粹比 PaaS 平台的話，就只是比誰方便而已，如果不想辦法增加更多價值，說實在真的很難繼續存活下去。

剛剛好，當時最紅的就是 n8n。

Note

n8n 是一套開源的工作流程自動化工具，可以幫助開發者自動化一些重複性的工作，像是資料抓取、資料處理、通知等等。

所以，當時 Zeabur 就把 n8n 加進了自己的模板中，讓大家可以快速部署一套自己的 n8n，再透過 n8n 去自動化一些流程，像是自動化部署、監控等等。

不得不說，我認為他們這個決定完全踩對了方向，就連我也覺得非常方便，我不需要花時間去弄 Docker，只要在部署時選一個 n8n 的模板就可以快速建立起來，省下許多時間，可以專注在工作流程的設計上。

而且不只開發者，許多非開發者也非常喜歡這種方便性，確實讓 Zeabur 成功走出了開發者的圈子，讓更多人知道 Zeabur 的存在，並開始用 Zeabur 來部署自己的服務。

越是方便的系統，越是有你所看不到的風險。

整個過程看似一帆風順對吧？其實很早期的時候，就發生過一次實習生操作失誤、誤刪叢集的事件（2023 年 10 月 27 日 Zeabur 台北區域服務故障報告）。

看到這邊，應該滿多人會開始噴：

：蛤？實習生可以拿到這麼高的權限？這也太誇張了吧？

：權限管理根本有問題吧？

：早知道有這事件我就不用 n8n 了！

諸如此類的話語吧？

但我認為對一間新創公司來講，這種事情早點發生反而是好事。

畢竟這個事件可以讓 Zeabur 開始思考怎麼管理權限，並建立一套完整的權限管理機制，讓使用者可以更安全的使用 Zeabur，而不是等到公司大了、使用者多了才出事，到時候就真的很難收拾了。

事後的故障報告裡也確實可以看到，他們重新設計了 IAM（雲端上用來管理誰可以做什麼的權限設定），讓開發者只拿到最小的操作權限，高風險操作還要另外經過管理員驗證跟 MFA（多因素驗證，像是登入後還要再輸入手機上的驗證碼）。

只是權限這種東西很難一次補完，補好了這一個洞，不代表別的地方沒有洞，這點我們後面再聊。

而且這件事情也剛好反映了許多公司的常態問題，也就是：

公司為了快速推出產品，往往會忽略一些安全性與權限管理的問題。

但這件事情有對錯嗎？

我覺得站在不同的位置，會有不同的看法：

  • 站在使用者的角度，當然會覺得這件事情很誇張。
  • 站在公司的角度，這件事情其實也算是「意外」，畢竟公司也沒有惡意，只是想要快速推出產品。

產品只要晚對手一點點，就可能被市場淘汰，最後被犧牲掉的，往往就是安全性與權限管理。

AI Agent 時代下，新創的資安難題

後來就是大家近期比較清楚的事件：

  • 2026/08/27：Zeabur 首度被入侵，大量使用者的環境變數被竊取（我也有受影響，剛好當時還在員工旅遊，只能看著 API Key 被燒掉 500 多美金）。
  • 2026/10/14：Zeabur 二度被入侵，而且這一次的規模比想像中更大。

八月那次 Zeabur 事後有公開事故報告（入侵路徑我們後面會再聊到），十月這次截至目前根因還在調查。

這個過程中，許多使用者最不能接受的，莫過於 Zeabur 在第一次被入侵後沒有第一時間發現（是靠外部回報才知道），第一封通知又低估了影響範圍，前前後後說法反覆不一，雖然事後有道歉，也承諾會改善這一塊，但對使用者來講，傷害已經造成了。

信任需要長時間建立，但摧毀只需要一秒鐘。

儘管還是有許多使用者選擇繼續相信 Zeabur（也有一部分人是因為方便才留下來），但這件事情對 Zeabur 的打擊已經很大了，當時我也發了個訊息給 Yuanlin，希望給他一點加油打氣。

Yuanlin

因為我相信沒有人會拿這種事情開玩笑，畢竟 Zeabur 對他來講，可以說是自己一手拉拔長大的小孩吧。

第一次入侵事件過後，Zeabur 看起來好不容易把事情處理完了，我也認為只要能撐過這一次，他們會變得更堅強。

只是這過程真的不容易，畢竟破碎的信任要重新累積，需要很長一段時間，但我相信沒有人想到竟然還會發生第二次入侵，而且這次的規模比第一次更大。再加上創辦人在信中提到的成長瓶頸、系統複雜度與維護難度，Zeabur 最終決定結束營運。

身為一間公司的創辦人，要親手寫下這封結束營運的信，心理壓力不知道有多大，從風光一時、人人推薦的 AI 部署平台，變成人人喊打的「資安漏洞平台」，甚至被拿來當作資安教材，這種落差真的很難想像。

這段過程中，我也看到不少人前後態度落差很大，前期各種推，後來出事就反過來跟著流量瘋狂罵。

當然不是說出事大家不能罵，畢竟使用者確實受到了實際的損失，但我覺得這件事情最可怕的莫過於「人性」，許多人為了搶流量在網路上攻擊 Zeabur，甚至連人身攻擊都出現，可是你有想過「他」願意讓這件事情發生嗎？

我覺得罵 Zeabur 做錯的決定完全沒問題，那些本來就該被檢討，Yuanlin 自己在公告裡也寫了「保護客戶的服務與資料是我們的責任，我們沒有把這件事做好」，當事人都已經認了，可是檢討決定，跟對一個人做人身攻擊，是兩件完全不同的事情。

可以罵做錯的決定，可是不需要罵那個人。

或許 Zeabur 的底層架構確實規劃有問題，但我認為這件事也值得我們一起想一想，因為它不只是 Zeabur 的問題，而是很多台灣新創都可能遇到的問題。

什麼問題呢？

我們常掛在嘴邊的 MVP（最小可行性產品），本身就很容易忽略安全性與權限管理，畢竟 MVP 的本質就是「快速驗證想法」，等想法驗證可行後，接下來要思考的是怎麼擴充、怎麼增加更多價值，而在這個過程中，安全性與權限管理往往又是最容易被往後排的。

接著，要回頭修正這些「一開始」就錯誤的決定跟架構，是一件非常困難的事情，畢竟這些決定與架構已經有人在用了，甚至有些使用者已經依賴它們在做事，這時候要怎麼修，對新創公司來講是一個很大的挑戰。

就如同在 JavaScript 中對 null 使用 typeof，會回傳 object 一樣。

這是 JavaScript 早期實作留下來的 bug，等大家發現的時候，已經有太多網站依賴這個行為了，想修也修不掉，最後只好一路留到現在。

Zeabur 八月那次的事故報告其實就是一個很好的例子。攻擊者一開始是從某個使用者部署在共享叢集（很多使用者的服務一起跑在同一組機器上）上的服務漏洞打進來，接著在快取裡撈到舊版的 API Key（Legacy API Key），試出一把有團隊管理員權限的 Key。

然後再從內部服務的環境變數裡挖到一組長期保留的 AWS root 金鑰（等於 AWS 帳號最高權限的鑰匙），最後一路走到正式環境的資料庫。

你會發現這條路徑上幾乎每一關都是權限的問題，跟 2023 年那次一樣，只是換了一個地方。

而報告裡還有一句話我覺得很關鍵：這條路徑上的共享叢集跟 Legacy API Key，在事故發生前就已經「進入淘汰階段」了，也就是說 Zeabur 自己也知道這些是該收掉的舊東西，只是上面還有使用者的服務在跑，沒辦法說關就關。

最危險的往往不是新功能，而是那個說好要關、卻一直還沒關的舊東西。

現在我們已經進入了 AI Agent 時代，大家都在部署各式各樣的 AI 工具，可是這些 AI 工具本身也可能就是破口。

像是 Zeabur 八月那次，攻擊者一開始打進來的地方，就是使用者部署的 AI 聊天工具 NextChat，利用的是它 MCP（讓 AI 可以串接外部工具的一種規範）功能的授權漏洞。

更別說 AI Agent 也能被拿來自動化的去搜尋漏洞、攻擊網站，攻擊只會越來越快，光靠人力去盯真的會越來越吃力。

接下來的時代，我們到底該怎麼在 MVP 的過程中兼顧安全性與權限管理呢？這是一個很大的挑戰。

當一個產品上線、開始有人使用後，它就不再只是「你的產品」，而是「使用者的產品」，你沒辦法控制使用者會怎麼使用它。

這點放在台灣新創身上又更明顯。

拿 Zeabur 來講，2025 年完成的種子輪是 200 萬美金（約新台幣 6,400 萬），可是前面提到的對手，Vercel 光是 2025 年 9 月的 Series F 一輪就募了 3 億美金，Render 今年 2 月也才又募了 1 億美金，累計募資來到 2.58 億美金。

同樣是做 PaaS，Vercel 一輪募到的錢，就是 Zeabur 種子輪的 150 倍。

在這種落差下，你能有多少資金去阻擋這些自動化攻擊？能有多少資金聘請資安專家來幫你規劃安全性與權限管理？還是每做一個產品，就要先花一筆錢在這上面？我想這個平衡點真的很難拿捏。

當然，像長期保留 root 金鑰這種事，跟錢多錢少其實沒有太大關係，可是當團隊的人力都拿去追功能、追成長的時候，這些「知道該收、卻還沒收」的東西，就很容易一直被往後排。

這時候又可以聊聊新創公司常見的另一個狀況，也就是「定位」問題。

相信也會有人認為是 Zeabur 的定位太過曖昧模糊，從一鍵部署的 PaaS、n8n 模板、AI Hub，一路到 2025 年募資時說要做的 AI DevOps 工程師，這也不可否認。

但許多時候，新創公司本來就會各種嘗試，看看哪些產品可以打中使用者，最後再收斂回來調整專注，只是這個過程中，只要有幾步沒踩穩，代價就會一路累積下來。

Yuanlin 在公告裡其實也寫到了這點：「這個系統從三年半前的一個快速開發專案開始，一路為了回應市場需求而調整架構、轉換方向，也累積了越來越高的複雜度與維護難度。」

對一間新創公司來講，每一步都是成本考量，但不去嘗試又不行，所以我覺得問題不在於該不該嘗試，而是每一次轉彎留下來的舊東西，有沒有人記得回頭收。

結語

寫到這邊，我想我的立場應該滿清楚了，一方面我是 Yuanlin 的朋友，另一方面我也是被盜刷了 500 多美金的使用者。

所以我不會說 Zeabur 沒有錯，長期保留的 root 金鑰、沒有權限範圍的舊 API Key、權限給太大的資料庫憑證，這些都是實實在在做錯的決定。

可是我也不覺得把這些錯誤變成對一個人的攻擊，能讓下一間台灣新創做得更好。

最後的最後，也提醒一下，如果你現在還在使用 Zeabur 的話，記得 12 月 1 日起專用伺服器會停止續費、共享叢集會暫停所有運行中的服務，12 月 31 日前全部關閉，資料記得提早備份搬家。

帳戶餘額退款跟資安事件損失賠償是兩個不同的申請，都要透過 Zeabur Support 提出唷。
