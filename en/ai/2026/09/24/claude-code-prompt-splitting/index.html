30 Days of Vibe Coding | Day 11: One Feature at a Time — How to Split Your Prompts

Intro

Yesterday we finally finished our first feature: "add an expense."

But... is that it? Nope. Next we're going to iterate on features and have the AI finish off the rest for us.

Sure, you could do it in one line: "Please read @SPEC.md and build all the remaining features."

But I really don't recommend that. It makes it easy to lose track of what it changed, and when something breaks, it's hard to trace and debug. You end up spending way more energy hunting down problems instead of focusing on building features.

So today's focus isn't really the features themselves. It's splitting the build into three rounds, with each round getting a clear prompt that tells the AI exactly how to build something that fits what you need.

Three parts of a good prompt

Personally, I think a good feature prompt has three parts:

  1. Current state: clearly describe what's on the screen right now and which part you want to change this time.
  2. What you want: what's the goal this round, and what are the specific fields and behaviors?
  3. Acceptance criteria: how do you know it's done right?

It might be a little hard at first to see why these three parts make for good feature work. Basically, all three are there to prevent one thing:

Stopping the AI from filling in too many blanks on its own, so its idea doesn't drift too far from yours.

AI is really smart these days, but sometimes it's a little too clever for its own good. So you have to describe what you want clearly, and then the AI can build something that actually fits.

Stop the AI from filling in too many blanks so its idea doesn't drift from yours

There's one more thing I want to point out, and it's about "current state."

Current state just means describing what you can see and what's happening right now, like...

  • Something on the screen looks off.
  • A button doesn't do anything when you click it.

You don't need to go dig up which folder the code lives in or what the file is called. That's not the Vibe Coding spirit at all — your job is to guide the AI toward the feature you want.

For the AI, the project is right in front of it. It'll read it on its own, and it'll find the file even if you can't name it. The real problem is the other way around:

It can't see the picture in your head. That's the part worth spending your effort describing.

With that out of the way, let's see these three parts in action.

Round one: category breakdown

First, build a good habit: whenever you start a "new feature," type /clear so you're working on a clean desk. That keeps earlier discussions and build steps from affecting this round. That influence is what we call "noise."

Once the desk is clean, we're ready for the first round.

After yesterday's "add an expense," the home page already shows this month's total and a list of this month's entries, so you know how much you've spent this month:

The home page shows this month's total and this month's entries

But an expense tracker can't be that bare-bones, right? A total and a list alone still don't make it easy to see where the money actually went. So next we're building a "category breakdown," so users can see clearly which categories their money goes to.

We're going to build the "category breakdown" from SPEC.md. Here's how I'd write the prompt (don't forget to turn on Plan Mode before sending it):

Text
The home page currently shows this month's total and this month's entries, but I can't tell which category I'm spending the most on.

Please read the "Category breakdown" part of section 5.1 in SPEC.md and build it. For placement, refer to the wireframe near the top of SPEC.md (below the total, above the list).

Acceptance criteria:

1. If this month I record Food 120, Food 80, and Transport 100, the screen should show two horizontal bars: Food $200 on top, Transport $100 below, with the Food bar longer
2. Categories with no spending this month shouldn't show up — no row of zeros
3. Round percentages to whole numbers. If three categories each have 100, show 33%, 33%, 33%. Adding up to 99% is fine, don't force it to 100%
4. Last month's data isn't included in the calculation

That prompt is really just the three parts:

  1. Current state: the home page has this month's total and entries, but I can't tell which category I'm spending the most on.
  2. What you want: add a row of category breakdown bars below the total.
  3. Acceptance criteria: four checks.

Notice I never said "please change this file or that component." We let the AI figure that out. What matters is telling it what you want the screen to look like. And if there's anything it's not sure about (like styling), it'll still ask you:

What should the bar length be based on?

The Plan Mode plan is long, but you don't need to read every word. Just focus on three things:

  • Which files is it going to touch?
  • What's it not doing?
  • What are the acceptance criteria?

The rest? Skim it so you get the general idea.

If it all looks fine, go ahead and click "Yes, and use auto mode" and let it get to work.

You'll notice that after you approve it, it doesn't start changing code right away. It first produces docs/plans/02-category-breakdown.md. That's the rule we added to CLAUDE.md yesterday kicking in, so from today on you don't need to remind it anymore.

Round two: edit and delete (with a bug left in on purpose)

With the category breakdown done, round two is editing and deleting entries. Sometimes we log the wrong thing or type the wrong amount, so this one really matters.

By now you should know what to do before starting the next round: type /clear first so you have a clean desk.

Then switch to Plan Mode and try something like this prompt for round two:

Text
Right now, clicking an item in the list on the home page does nothing. Please read "Transaction list" in section 5.1 and "Delete" in section 5.3 of SPEC.md.

When the user clicks any item in the list, open an edit form. The form shows four fields, pre-filled with that item's existing data. When the user finishes editing and clicks save, the form closes. The edit form also needs a "Delete" button; clicking it shows a confirmation prompt, and once the user confirms, that item is deleted and the form closes.

One more thing: I want you to deliberately set up a controlled debugging exercise. On purpose, use "which position this item is in the list on screen" to identify the item for editing and deleting — don't use each item's id. Add the comment "TODO for later practice: switch to id" next to the related code, and don't fix it to use id yet.

Acceptance criteria: add three expenses on the same day in a row. Clicking the middle one opens the edit form, clicking delete shows a delete confirmation, and after a successful delete the form closes and only the middle item disappears from the home page list. If you click cancel, nothing changes.

Along the way, it'll probably ask you how to build the popup:

Asking how to build the popup

Same as before, you can just go with "recommended" unless you have other ideas.

I need to explain something here. Normally, deleting by index isn't a good approach. This is a known bug I designed on purpose — the right way is to use an id (a unique value). The AI would normally fix this on its own, which is why we have to specifically tell it to make the mistake.

If the difference between index and id doesn't quite click, here's an example: say there are 30 students in a class, and you take attendance by "the Nth student." If they secretly swap seats, you'll have a hard time calling the right person. Think of an id as the student's ID number or name — even if they swap seats, you'll still get the right person.

Once that makes sense, you should get this Plan Mode plan. Same deal: if it looks fine, click "Yes, and use auto mode" and let the AI build it.

Why set up a scenario like this? You're probably wondering. It's to let you experience one thing for yourself:

Passing review doesn't mean there are no bugs. It just means you didn't happen to test that scenario.

After the AI finishes, tell it:

Text
Please commit the current progress with the message: "Practice: edit and delete, index bug left in"

That way, when you (or the AI) go bug hunting later, you'll know this version has a bug in it.

You might have noticed this message doesn't follow the "Feature name: short description" format we set in CLAUDE.md. That's on purpose. Starting it with "Practice:" means you can spot this teaching landmine in the git history at a glance, and it won't get mixed up with normal feature commits.

Round three: switching months

Round three works pretty much the same as the first two. /clear first, switch to Plan Mode, then try something like this prompt:

Text
The top of the home page is currently stuck on this month, and there's no way to see other months' data.

Please read "Month switching" in section 5.1 of SPEC.md. Add an arrow on each side of the year/month line to switch to the previous/next month, plus a "This month" button to jump straight back.

Acceptance criteria: press the left arrow repeatedly to go back three months, and the total, category breakdown, and list should all switch to that month's data. Then click "This month" once to go straight back to the current month. After coming back, the "This month" button disappears, but the left and right arrows don't shift position because of it.

The process is pretty much the same as the first two rounds, so I won't repeat it.

After finishing month switching, these three rounds should leave you with a pretty strong feel for why "one feature at a time" works so well.

Flowchart for building one feature at a time

Why type /clear every time?

Across these three rounds, I kept stressing that you should /clear first.

That ties back to the Context Window idea from Day 6 (a desk with limited space). Whatever the AI Agent built earlier (the Context) can pollute what comes next. So usually, every time we start a new round of work, we /clear once so the previous round doesn't affect the current one.

So does our project's shared understanding get wiped? Nope.

When you run /clear, the AI does clean off its desk, but it also puts CLAUDE.md back on it. Then when you start the next round, it works from what's in CLAUDE.md (and pulls in SPEC.md too), so the previous round doesn't bleed into the current one.

So you can use /clear with total peace of mind.

Note

Just to be clear, "one feature at a time" doesn't mean chopping features up as fine as pickles. Aim for a size you can "finish in one go and review at a glance." The category breakdown is one round, edit and delete is one round, but "the color of the delete button" doesn't need its own round — just handle it as part of that round.

If you've been following along exactly, your git history should now have a "Practice: edit and delete, index bug left in" commit. That's the only landmine in the whole series that gets to survive overnight. Tomorrow we'll set it off and then fix it.

Wrapping up

We've finally made it to Day 11. Today we ran three rounds of feature work, all using the same approach:

  1. /clear to clean the desk (start a new conversation), switch to Plan Mode, describe what you need using the three prompt parts (current state, what you want, acceptance criteria), read the plan before approving, review against the criteria when it's done, and commit once it passes.
  2. Start every round in Plan Mode. The plans might be long, but as the project's foundation gets more solid, there's less and less you need to read.
  3. Don't be afraid of /clear wiping important info. Every clear puts CLAUDE.md back in, and the shared understanding that really needs to stick around is already written into SPEC.md and CLAUDE.md.

At this point we've finished all six items on the "In" list in section 3 of SPEC.md. The expense tracker app can now "add, edit, delete, and switch months," and the data gets saved.

But there's still that landmine we planted in the project. Tomorrow we'll walk through a full bug-fixing session live, so hold off on sneaking in a fix before then.
