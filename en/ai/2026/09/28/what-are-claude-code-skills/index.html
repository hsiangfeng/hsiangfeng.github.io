30 Days of Vibe Coding | Day 15: What Are Skills? Teaching AI How You Get Things Done

Intro

We've made it to Day 15, which is also the first day of Week 3!

While building the MVP last week, you probably noticed a few problems. For example, you kept saying the same things over and over, like how commit messages should be written.

Sure, CLAUDE.md has some rules in it (the general ones), but there's still stuff that never made it in there. On top of that, CLAUDE.md has a recommended line limit (somewhere around 200–250 lines). Cram all of this in and it gets way too bloated, but repeating it every time is exhausting.

So today we're going to meet something new: the "SKILL."

SKILL: your own personal ability

So what is a SKILL? In short, it's just a folder plus a Markdown file (a plain-text kind of file, like CLAUDE.md).

"That simple?" you might be thinking.

Yep, it really is that simple.

But what it can do is anything but simple, because a SKILL can contain things like:

  • Steps
  • Rules
  • Examples

It can even include ready-made helper code, so you can just use it whenever you need it.

Still hard to see why that's so powerful, right? Let's switch to a more gaming-style way of looking at it. That might make it click.

Say you're playing an RPG. The character you control usually has a bunch of skills, like "Fireball," "Heal," or "Invisibility." Those are the skills you can use in the game.

So when you want to use one of them, you just shout:

"I'm casting Fireball!"

And your character casts it for you.

But why does just saying "I'm casting Fireball!" actually cast it? Normally, to cast a specific skill like "Fireball," your character needs to know how it's cast, the steps, the rules, and so on. If you had to set all that up yourself, you'd probably have to draw a magic circle, gather your magic ingredients, chant the incantation, and so on before the spell goes off. But once it's packaged up as a skill, you might only need to chant and grab your ingredients, skipping the tedious magic-circle part entirely and casting it right away.

Fireball

Once that makes sense, we can bring the idea back to SKILLs in the AI world (they work just like a game character's skills). You just tell Claude you want to use a certain SKILL, and it'll handle the steps, rules, examples, and everything else that skill needs, so you can get the task done faster and more efficiently.

Is SKILL a Claude-only feature? Nope. Pretty much every AI vendor out there offers SKILLs. But since this series is built around Claude Code, I'll stick to Claude Code's SKILLs. For other vendors, a quick search will usually turn up their setup, and it's all very similar anyway.

So where do SKILLs live? Let's first look at what one looks like.

First, you have a .claude folder. Inside it is a folder called skills, and every SKILL is its own folder with a SKILL.md inside:

Text
············.claude/
└── skills/
    └── commit-message/   ← this folder's name is the SKILL's name
        └── SKILL.md

That skills folder can basically live in one of two places:

  • Inside your project: This is a "project SKILL." It travels with the project, so when your team pulls the project, everyone shares it (which also makes it handy for enforcing team rules, like... commit message format).
  • On your computer (that's ~/.claude/skills/, where ~ means your home folder: /Users/your-name on a Mac, C:\Users\your-name on Windows): This is a "personal SKILL." By default it applies to every project you open, but it never gets committed into any project.

And there are two ways to trigger one:

  • You type /folder-name (for the example above, that's /commit-message) to call it up manually.
  • The AI decides on its own whether the current task matches a SKILL's description, and if it does, pulls it out and uses it.

Pretty interesting, right? Let's keep going and see what else SKILLs can do.

There are actually three kinds of SKILLs

By now you should have a basic idea of what a SKILL is. Next I want to break the concept down a bit further.

Because I think SKILLs can be split into three types:

  • Knowledge:
    • These hold rules, conventions, and style, like "how commit messages should be written in this project" or "what are the main Vue 3 syntax patterns?" That sort of thing.
    • This kind of SKILL usually isn't about getting the AI to do something. It's about keeping the AI from using outdated or wrong information. In RPG terms, it's like a passive skill: always on. You don't have to shout or call it, the AI decides on its own and attaches it.
  • Workflow:
    • These hold step-by-step SOPs, like "how to fix a bug" or "what to run before going live." You usually only call this SKILL when you need it to do that thing.
    • You don't want the AI running this whole pile of steps for no reason. After all, a single deploy for a single product might involve a lot of steps. In RPG terms, this is an active skill: you shout the move (that's /name), and only then does the AI cast it for you.
  • Tool:
    • The last kind is a bit special. It includes ready-made code (usually under scripts/). The upside is the AI doesn't have to rewrite it every time, it just runs that code, like "turn CSV data into a chart" or "batch-compress images" (I personally batch-compress images all the time). In RPG terms again, it's like a "magic item with a skill built in": once it's equipped, the AI can use that item's skill directly.

Why split it up this way? It also kind of answers the question of triggering. For a knowledge SKILL, you want the AI to decide by default whether to use it (would you really want to keep typing /please-use-taiwanese-terms all the time?). For a workflow SKILL, you don't want the AI running it on its own (a workflow can involve a lot of steps). That's why there are two ways to trigger them.

Of course, this split isn't something the official docs define (they only distinguish between "reference knowledge" and "task workflows"). It's just that I think splitting it into three makes it easier to know when to use what, and it keeps a SKILL from turning into a mess where everything gets stuffed in.

The complicated relationship between SKILLs and slash commands

Next, let's talk about the complicated relationship between SKILLs and slash commands. If you've been learning Claude Code on your own, you may have come across something called commands. The idea there is "custom slash commands."

In earlier posts we tried built-in slash commands like /rewind, /clear, and /compact. Those are default commands that Claude Code provides, and you can't change them. So to solve that problem (back before SKILLs existed), Claude Code let you define your own commands. These custom slash commands live under .claude/commands/, and they're also .md files, written in Markdown...

Yep, that's right. They're about 87% the same as SKILLs.

So which one should we actually use? Honestly, I'd just tell you to use SKILLs, since they work across different AI vendors (like Codex, Gemini, and so on).

Here's a table to make the relationship between Skills, built-in slash commands, and custom slash commands clear:

Built-in slash commandsCustom slash commands (old)Skills
Examples/help, /clear, /compact.md files in .claude/commands/Folders in .claude/skills/
What it isFeatures hardcoded into Claude CodeCustom prompt templatesA full skill package

How to split the work with CLAUDE.md

Next up is another topic that can get confusing: "Should I write this in CLAUDE.md or in a SKILL?"

It's actually simple. Just remember one line:

One is the constitution, the absolute highest rule. The other is a skill you only use when you need it.

That's also why things were set up the way they were earlier. Every /clear (/new) reloads CLAUDE.md, which is what makes it the "constitution." A skill only gets loaded when you need it (technically the skill's description does get loaded, but not the whole skill package. We'll get to that later). So you only know the skill is called "Fireball," but you don't know how it's cast, the steps, the rules, and so on. All of that only gets loaded when you need it.

This design is also a way to save on Context usage.

Skills you can install: a first look at /plugin

Now that you know the SKILL basics, you probably think we're about to write our own SKILL, right?

Nope. Writing your own SKILL from scratch is a bit too hardcore for now, so first let's try another way: "installing one."

"Huh? Installing one?"

Yep. Basically you use a SKILL someone else already wrote, so you don't have to start from zero.

So open your terminal, type claude to start Claude Code, then type /plugin. You can browse around in Discover:

The Discover tab after typing /plugin

As an example, let's install the skill-creator SKILL. Once you find it, press the space bar to select it, then press Enter:

Selected state

Next, I personally recommend installing this SKILL at the "user" level. It's a SKILL for my own use and has nothing to do with any specific project, so I install it for myself instead of just for this project:

Installing to the personal folder

Note

In short, the skill-creator SKILL helps you create new SKILLs. If you want to package up your own SKILLs, it's super handy.

If you can't be bothered to hunt for it, you can also just type the command:

Text
/plugin install skill-creator@claude-plugins-official

Once it's installed, don't forget to type /reload-plugins so it takes effect.

You might notice something odd here. We installed a SKILL, but it didn't go under ~/.claude/skills/. It went to ~/.claude/plugins/ instead.

The real difference between those two folders isn't "where things go," it's "who's in charge of managing them."

~/.claude/skills/ is the area you manage by hand. You drop SKILL folders in, update them, and delete them yourself. Claude Code just reads them. It doesn't know or care where those files came from.

But stuff installed from a marketplace is different. Claude Code has to keep records for you: which marketplace a package came from, what version it is, and when it was installed. Only with those records can it check for updates and remove things for you later. So those records and files all get kept under ~/.claude/plugins/, where it manages them itself (if you're curious, open ~/.claude/plugins/installed_plugins.json and you'll see the install records one by one).

It's basically like your phone. Files you copy onto your phone yourself won't get updated by the system. But apps installed from the App Store can be auto-updated and removed with one tap, because the store knows where they came from and what version they are. That's why those apps live somewhere the system manages itself.

There's also a more fundamental reason...

"A plugin is not the same as a skill."

A skill is just one of the things a plugin "might" carry. A plugin can also include custom slash commands (yep, the ones we just talked about) and other more advanced features. So what you're actually installing is "a whole plugin package," and naturally it goes under ~/.claude/plugins/.

And because plugins are managed separately, the skills they bring in get the plugin's name attached when you call them, in the format /plugin-name:skill-name. So you don't have to worry about them clashing with the SKILLs you put in ~/.claude/skills/ yourself.

So how do you know what a plugin will install? Before installing, you can open that plugin's details page. There's a Will install field that tells you what it's going to bring in:

A plugin's details page showing what it will install

Note

If you can, try to only install plugins from the official marketplace. Official plugins go through review, so they're relatively safer.

Wrapping up

That pretty much covers SKILLs, so let's do a final recap:

  • A SKILL is really just a folder plus a SKILL.md. Put it in a project and it belongs to that project. Put it in ~/.claude/skills/ and it works across all your projects (basically, your whole computer gets it).
  • There are two main ways to trigger one:
    • You call it manually by typing /name.
    • You let the AI decide from the description whether to use it and call it.
  • SKILLs can be split into three kinds:
    1. Knowledge (passive skill, the AI attaches it on its own).
    2. Workflow (active skill, only cast when you shout the move).
    3. Tool (a magic item with a skill built in, comes with code it runs directly).
  • Custom slash commands are about 87% the same as SKILLs, but I'd just go with SKILLs, since they work across different AI tools.
  • CLAUDE.md is the top-level "constitution" that loads every time. A SKILL is a "skill" that only gets loaded when needed. Things you have to follow every time go in the constitution, and things you only use now and then get packaged as a SKILL.
  • SKILLs can be installed (/plugin), but before you install, check what Will install is going to bring in, and stick to the official marketplace as much as possible.
  • There are two ways to get them:
    • SKILLs you write yourself go in ~/.claude/skills/.
    • Installed ones get kept in ~/.claude/plugins/.

If that all makes sense, that's where we'll stop for today.
