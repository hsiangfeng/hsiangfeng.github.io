30 Days of Vibe Coding | Day 4: Your First Task — The Smallest Loop for Changing Code

Intro

If you've made it to this chapter, I'm going to assume you've already got Claude Code installed, because today we're finally getting our hands a little dirty.

The goal today is small, though. We're going to use a tiny practice file to run through one full loop of "ask it to do something → see what it did → decide whether to keep it → pull it back if you change your mind".

Don't underestimate this loop. Once we start building the expense tracker app later in the series, pretty much everything revolves around this exact flow and mindset.

Create your first practice file

Before we start, let's warm up a bit. Open your terminal and either drag the claude-playground project folder into it, or just cd into it:

Bash
cd claude-playground

Then copy and paste the command below to quickly create your first index.html practice file:

Bash
··········echo '<!DOCTYPE html><html lang="zh-Hant">
<head>
  <meta charset="UTF-8">
  <title>我的練習頁（是 Ray 不是 Array）</title>
</head>
<body>
  <h1>Hello，這是我的 Vibe Coding 練習頁</h1>
  <p>目前這裡什麼都還沒有。</p>
  <a href="https://israynotarray.com/" target="_blank">是 Ray 不是 Array</a>
</body></html>' > index.html

Terminal screen after creating index.html

The content is really simple — just a basic heading, a line of text, and a link. The simpler the file, the more you can focus on how Claude Code behaves, instead of getting distracted by complicated code.

Note

If creating the file doesn't go smoothly, you can grab the full example files here: https://github.com/hsiangfeng/ithelp-2026-vibe-coding. Just click "Code → Download ZIP" and you'll have the practice files.

Ask questions before you change anything

Once that's ready, type claude in the terminal to launch Claude Code. Before you do, double-check that you're actually inside the claude-playground directory, otherwise you might run into some weird problems.

Also, your permission mode should be the default "manual mode on" (which the official docs call default). That means every time it wants to touch your files, it'll stop and ask you first. We'll get into the details on Day 5.

Claude Code default permission mode

So we're not going to ask the AI to change anything right away. Instead, we'll first have it confirm "what it can see and what it understands right now", like this:

Text
What's in this folder? What's inside index.html?

A lot of people get curious at this point: "Why bother?"

There are actually two reasons:

  1. To confirm Claude Code sees the same files you do. This also catches cases where you didn't actually end up in the claude-playground directory, or the file didn't save, or got saved in the wrong place.
  2. To let Claude Code understand the current state first, so it doesn't misread whatever you type next and make changes you didn't expect.

Claude Code replying with the file contents

As long as your result looks similar to (or the same as) mine, you're in the same spot I am, and you can keep going.

Note

Of course, even if you don't ask "What's in this folder? What's inside index.html?", it'll go read the files on its own anyway. It's just a personal habit of mine to check what it can see first — it avoids a lot of unnecessary misunderstandings.

A controlled failure: give it a vague prompt on purpose

I'm not going to start by showing you the "right answer". I think you should experience the wrong way firsthand, because that's how you'll actually understand why the right way is better.

So copy and paste this into Claude Code's input box:

Text
Make this page look better. You decide how.

Don't be scared! Go ahead and send it. It's just a practice file, and every time Claude Code receives a prompt, it automatically saves a restore point (this mechanism is called a checkpoint). Even if things go sideways, you can get it back.

Tip

A line like "Make this page look better. You decide how." is what we call a prompt (as in "writing a prompt"). Anything you send can be called a prompt — it's basically the thing you want Claude Code to do. Definitely remember this one.

Along the way it may ask you some permission questions. That red-and-green chunk in the middle of the window is the change it's planning to make (red is what it wants to delete, green is what it wants to add — I'll teach you how to read it properly in a bit). For now, just glance at it so it looks familiar. Then you'll see three options:

  • Yes
  • Yes, allow all edits during this session (shift+tab)
  • No

Claude Code asking for permission

Pick "Yes" here, which means you're approving this one change, and it'll start editing the file. (Please don't pick "Yes, allow all edits during this session (shift+tab)" — that option auto-approves every edit after this one, which is really not safe for beginners.)

Then Claude Code will tell you what it changed and what it did:

Claude Code explaining what it changed

So how do you actually look at the result? Easy, just tell it:

Text
Please open index.html for me. I want to see the result in my browser.

If a permission prompt like the one below pops up, no need to worry — just allow it:

Claude Code asking for permission

You should now see something like this, and it'll probably look a bit different for everyone:

The result of opening index.html in the browser after Claude Code's changes

Pretty interesting, right? The same prompt can produce all kinds of different results. That's AI randomness, and that randomness is exactly why you can't predict what it's going to turn the page into — which leads to the problem of "you can't verify it".

You might actually think the design looks pretty nice and wonder, "So where's the failure?"

Try answering these three questions:

  1. What exactly did it change, in total?
  2. Why did it change it to this, and not something else?
  3. Does this count as "done right"? What's your standard for judging that?

A bit hard to answer, isn't it? Exactly. That's the first big takeaway: "you can't control it". Just like we saw, the same sentence — "Make this page look better. You decide how." — can give completely different results for different people, different models, or even the same person sending it twice.

Because you didn't define any acceptance criteria or tell it what style you wanted, the AI has no choice but to fill in the blank called "looks better" with its own imagination. And you have no way to tell whether it got it right or wrong. That's why sending the exact same sentence again might give you something totally different.

So whether the page looks nice is secondary. The real problem is that you've lost the ability to verify. You can't say whether this result is right or wrong — only whether you like it or not.

If you're just building a toy for yourself, that's fine. But if you want to build something people can actually use, "can't verify it" becomes a serious problem, because you have no idea how far you are from the goal, or what the next step should be.

Pull it back with /rewind

Now that we've been through that first task, let's undo the failure. This is where the checkpoint mechanism I mentioned earlier comes in.

Type /rewind in the input box, or press Esc twice while the input box is empty — that also brings up the restore menu. You should see your conversation history. Find the "Make this page look better. You decide how." line and select it.

The rewind menu

The menu first lists the prompts you've sent in this conversation. Pick which one you want to go back to (here, the "Make this page look better. You decide how." one), and then you should see these choices:

  1. Restore code and conversation
  2. Restore conversation (only the conversation; your code stays as-is)
  3. Restore code (only the code; the conversation stays as-is)
  4. Summarize from here (compress the conversation from this point on into a summary)
  5. Summarize up to here (compress everything before this point into a summary)
  6. Never mind

Pick "Restore code and conversation". That puts both the code and the conversation back to how they were before you sent that vague prompt, and the prompt itself will be waiting in the input box so you can quickly edit it.

Note

Heads up: /rewind only restores changes made with Claude Code's editing tools. If anything got deleted or moved with a Bash command along the way, that can't be restored. That's why real projects almost always pair this with Git (a tool that saves every version of your files — we'll formally introduce it in a later chapter), which is much safer.

By now you've probably noticed that "wander off, then pull it back" is a big deal, and it's actually one of the key skills in Vibe Coding. Going off track isn't the problem. Not being able to get back is.

Give it a small task you can verify

Next, I'll show you a small task that can be verified (and I mean really small). Delete the "Make this page look better. You decide how." text in the input box and replace it with this:

Text
Add a button to the page. When I click it, the whole page's background color changes to a random color.
Note

Quick tip: pressing Ctrl + C in the input box clears the whole thing instantly, so you don't have to delete it character by character. Just be careful — if you press it while the AI is still thinking, it'll interrupt it. So wait until it's done replying first.

You might be thinking, "How is this verifiable?" It actually is:

  • Is there a button on the page? You can tell at a glance.
  • Does the background change color when you click it? One click and you know.

Right or wrong, there's no gray area.

As for what the button looks like, where it goes, or what color it is — we let the AI decide, because those aren't what we're checking this time. What matters is "is there a button, and does clicking it change the color?" That's what a verifiable small task looks like.

After you send it, don't rush to look at the result. Read its reply first. Usually it'll tell you what it changed and which tools it used, and then ask whether you want to open the browser to see the result.

Claude Code calling the write tool

Note

Read, Edit, and Bash are Claude Code's built-in tools, and they're the three beginners see the most: reading files, editing files, and running commands. It decides on its own which tools to use for each task. For now, just recognizing these three is enough.

In theory, your browser should open at this point. If it doesn't, you can tell the AI:

Text
Please open index.html for me. I want to see the result in my browser.

Congrats — you've just described a minimal task that "can be verified".

Reading the diff: red is deleted, green is added

All that red and green from earlier actually has a proper name: it's called a diff, meaning "difference" — the difference between the code before and after a change.

This is your most important tool for tracking what Claude Code did, and it's also what you base your decision on when choosing whether to accept a change.

Remember this:

  • Red lines are what it wants to delete (usually starting with -)
  • Green lines are what it wants to add (usually starting with +)

Build this habit: at least glance at what it touched and check whether it matches what you expected before you hit Yes.

The diff confirmation screen, with deletions in red and additions in green

Below that, there are basically three options:

OptionWhat it meansWhen to use it
YesApprove this one time onlyUse this one for pretty much everything early on
Yes, allow all edits during this sessionAuto-approve every edit for the rest of this conversationWhen you already trust where this task is heading
No, and tell Claude what to do differentlyReject it and tell it what to changeWhen the direction's off or you want a different approach

The exact wording may differ slightly depending on your version, so go by what's on your screen.

The third option deserves a bit more explanation. It's not just a cancel button — you can follow it up with a sentence that steers it back on track. For example, "The button text should be 'Change background color', not 'Click me'":

Text
The button text should be "Change background color", not "Click me".

It'll redo the change and show you a new diff to confirm.

The diff confirmation screen, with deletions in red and additions in green

Note

I won't walk through the third option in detail here — give it a try yourself.

Wrapping up

Let's recap today's minimal loop. This diagram should make the whole flow clearer:

Claude Code minimal loop diagram

  • Ask before you change: asking questions is zero risk. Let it understand the current state, and make sure it didn't get the wrong idea.
  • Give it specific, small tasks, and watch its tool messages along the way so you know what it touched.
  • At least glance at the diff before hitting Yes. If the direction's wrong, use the third option to steer it straight.
  • If you regret something, use /rewind (or press Esc twice). Just remember it can't undo changes made through Bash.
  • We deliberately let a vague prompt fail once. The failure wasn't that the page looked ugly — it was that you "couldn't say whether it was right or wrong". Then we used "restore → rewrite the request → verify again" to pull things back on track.

That's it for this one. See you tomorrow.
