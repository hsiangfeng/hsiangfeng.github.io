30 Days of Vibe Coding | Day 9: Setting Up the Project with CLAUDE.md and git init

Intro

"SPEC.md is done, so I can finally tell the AI to start writing code, right?!"

Hold on. If you think a finished SPEC.md means you can jump straight into "go build it," that's the wrong idea and the wrong process.

So don't grab your SPEC.md and run off to the AI just yet.

It already picked your tech stack. Did you agree to it?

First things first: if we're building an expense tracker app, we have to decide what tech to build it with. But as non-engineers, how are we supposed to know what Vue, React, Svelte, Angular, Next.js, Nuxt... all these names even mean?

Don't panic. Open yesterday's SPEC.md (you can check the example file on GitHub #day9) and scroll down to section 6, "Tech decisions." You'll notice something interesting:

While Claude was interviewing you, it quietly went ahead and picked the tech for you.

Things like Vue 3 + Vite, Tailwind CSS, no Router, no Pinia — it even thought through the file structure. But here's the question... did you ever agree to that? Do you even know what those things are?

AI is smart, but it can also be a bit of a busybody. And that busybody streak is exactly how "AI amplifies your vagueness" comes true. In the last post we were turning an idea into a spec — we never talked about tech choices at all. But the AI figured it might as well get that ready for you, and you happened not to notice what it picked. So now SPEC.md has a tech decision baked in.

To be fair, the decision isn't necessarily wrong (you'll see in a minute that it actually picked pretty well). But "the AI decided" and "you signed off" are two different things. So today we're going to make that call properly and lock in the tech stack.

Go into the money-note folder, start claude, and type:

Text
Please read SPEC.md.
Based on this spec, what tech would be the best fit?
Give me two or three options, explain the pros and cons of each, and then give me your recommendation.

A few things matter to me. I want it to be...

- Simple enough
- Mainstream enough
- Easy to deploy
Note

If you're worried the AI will skim or misread things, you can ask it: "What's in the SPEC.md file in this project? List its section headings first, then explain what's in it." That way you can confirm it actually read SPEC.md.

Discussing tech choices with Claude — it lists its recommendations and reasons

Here's the fun part: it labels the original choice from SPEC as "Option A (SPEC's original plan)" on its own, and only then gives you alternatives. In my conversation it came up with three:

  • Option A: Vue 3 + Vite + Tailwind (SPEC's original plan)
  • Option B: Plain HTML + JS + CSS, single file, no build step
  • Option C: React + Vite + Tailwind

And in its write-up you'll spot a couple of key points:

  1. This app has no need for a server at all
  2. How much help you need with reactivity

At this point I bet you're full of questions. What does "how much help you need with reactivity" even mean? The trick hasn't changed — just ask the AI to explain it in plain language:

Text
I don't understand "how much help you need with reactivity." Can you explain it in plain language?

It'll tell you that "reactivity" means "when the data changes, the screen updates automatically."

Asking Claude about "reactivity" — it explains it in plain language

Note

The screenshot is from a Chinese conversation, where the AI picked a slightly unusual word for "reactive." That's just a quirk of its training data — don't worry about it. What matters is that it explained the idea clearly.

After reading all that, I'd still recommend keeping the original plan, unless you want to challenge yourself with a different stack. Use this prompt to have the AI add a decision log entry:

Text
I've decided to keep Option A (SPEC's original plan): Vue 3 + Vite + Tailwind.
Please add this entry to the "Decision log" in SPEC.md: the tech stack stays as originally planned, confirmed after comparing it with plain HTML and React. Don't change anything else.

Writing decisions down will absolutely help you when you look back in a few days, a few months, or even a few years. These are some of the most valuable assets in your project.

Claude adds the decision to the decision log in SPEC.md

Note

The options it lists also take your past conversations and background into account (it knows I write Vue all the time), so the options and reasons you see might differ from mine. That's totally normal. The point isn't to copy my answer — it's to actually understand the reasons it gives you before you say yes. If you're not building an expense tracker, the process is the same: hand over the spec, ask for options, read the reasons. Different requirements will land on different answers.

So that's our stack settled: Vue 3 + Vite for the UI, Tailwind for styling, and LocalStorage for saving data. As for where to deploy it... we'll get to that in a later post.

Getting your environment ready

Think you can start building now? Nope. Next up is the dev environment.

Honestly, I think this is where a lot of beginners get stuck, because you have to install an extra program: Node.js.

Open the official Node.js download page and grab the LTS version (Long Term Support — just click the button marked LTS; if the version number is newer than in my screenshot, that's normal).

Node.js download page: https://nodejs.org/en/download

Node.js download page

Then pick whichever install method you like. I won't go into detail here since Windows, macOS, and Linux are all a bit different — just follow the instructions on screen.

Node.js installer

On top of that, you'll need to install git (the version control tool):

Git download page: https://git-scm.com/downloads

Git installer

Before we start, we need to check that these tools are actually installed. "Installed but not working" is where beginners die the most.

Open your terminal (if you're still inside Claude Code, type /exit first, or just open a new terminal window) and run each of these:

Check your Node.js version:

Bash
node -v

Check your npm version:

Bash
npm -v

Check your git version:

Bash
git --version

There's really only one thing that matters: all three commands should output a version number.

If any of them does nothing or throws an error, copy the command you ran along with the full error message and ask claude.ai. For environment problems like this, pasting the complete message usually gets you a fix pretty fast. Sort it out before moving on, because everything after this depends on these three.

Finally, I strongly recommend installing the Claude in Chrome extension for your browser. Later on it lets the AI drive your browser to debug things, so it's worth setting up ahead of time.

Let the AI set up the dev environment

So what now? Do we have to type a bunch of commands like an engineer? Nope.

Just tell the AI:

Text
Based on the spec in SPEC.md, please set up the development environment for me. Don't start building features yet.

Yep, it's that simple. The AI will probably ask you a few questions along the way.

Note

I often add "don't start building features yet" on purpose, because the AI loves to be helpful and jump straight into coding before your environment is even ready, which makes mistakes a lot more likely.

Claude Code setting up the dev environment

Once it's done, your folder will have a bunch of new stuff in it (package.json, src/, node_modules, and so on). That's the skeleton of a Vue project. You don't need to get to know each of them right now — I'll introduce them as they come up.

When it's ready, tell the AI:

Text
Please start the project's dev server. I want to preview the project.

The AI should tell you it has started the dev server and give you a URL. For Vue it's usually http://localhost:5173/ (it might be different, so go with whatever URL the AI gives you). Paste that URL into your browser to see the project.

Claude Code starting the dev server

Note

Different tech stacks start their dev servers in different ways, but it almost always ends with a URL you can open in your browser to see the project.

The browser after Claude Code starts the dev server

And with that, the basic environment is sorted.

git init: the undo button for Vibe Coding

Next, let me talk a bit about something really important in Vibe Coding — call it an undo button, or a time machine: Git.

I think Git is the single most important tool in any Vibe Coding project, and it's something you really have to get comfortable with. You don't need to keep typing commands like an engineer does:

Bash
git init
git add -A
git commit -m "Feature name: short description"

But you're going to really need its "undo button" and "time machine" powers.

What do I mean? Back in Day 4's wrap-up I said: "If you regret a change, use /rewind (or press Esc twice), but keep in mind it can't undo changes made through Bash." So once the AI runs a bash command, /rewind can't save you. Git can, because everything gets recorded in commits, and you can jump back to whichever version you want.

Note

Think of a "commit" as a save point in a video game. Every commit is a complete save, and you can go back to any of them.

So what do we need to do with Git? Nothing, actually.

The person running these commands is the AI, not us humans. All you need to do is make sure Git is installed and tell the AI:

Text
Please make sure to initialize my code with git init.

And you're set.

Note

Heads up: today we're only doing the "initialize" part. We haven't made any commits (save points) yet. The first save point shows up tomorrow, after we finish the first feature and it passes review. That also lines up with the dev rule we're about to put in CLAUDE.md: only commit after a feature passes review.

The AI's constitution: CLAUDE.md

Last thing for today — we need to meet CLAUDE.md.

This thing is really, really, really important. Why? Pretty simple: CLAUDE.md gets loaded automatically into every conversation. It's like the project's constitution, holding the project's rules, tech stack, command conventions, and so on.

In earlier posts, whenever we typed /clear or opened a new conversation, all the settings we wanted would just disappear. But with CLAUDE.md, the settings and rules you want, like...

Markdown
- Always reply in English
- ...

...get loaded back in automatically, so you don't run into the "it forgot my settings" problem anymore.

Note

It's a good idea to keep CLAUDE.md under 250 lines, and to put in rules the AI can't figure out just by reading the code — things like "always reply in English."

Creating one is simple, and there are usually two ways:

  • Create it manually: add a file named CLAUDE.md in the project root and write your rules in it.
  • Use the built-in /init command: it scans your project and generates a CLAUDE.md automatically. The generated version mostly describes how things are right now, so we'll add the "dev rules" ourselves.

Which is better? If you're a total beginner, I'd just use /init — it's easier. If you've got some experience, creating it by hand gives you more precise control over what goes in.

Here's the CLAUDE.md that /init generated for me, for reference (day9#CLAUDE.md). Mine is in Chinese, but you'll most likely get an English one out of the box, so you can use it as is.

The CLAUDE.md generated by /init

There's one more small tweak to make: defining a simple dev workflow. Just send this prompt to the AI:

Markdown
Please add the following dev rules to CLAUDE.md, and follow them in every conversation:

- Commit once each time a feature passes review, using the commit message format "Feature name: short description"
- Write commit messages in English

Adding dev rules to CLAUDE.md

Today's mini challenge

As usual, here's a small challenge. Try to confirm the following:

  • node -v, npm -v, and git --version all show a version number.
  • Ask the AI to start the server, and you can see the page in your browser instead of "This site can't be reached" or an error screen.
  • SPEC.md and CLAUDE.md both live in the root of money-note/.

Pretty easy, right? If something goes wrong, go back through the earlier sections, or take a screenshot and ask the AI. It can usually sort it out for you.

Wrapping up

Let's recap what we did today.

It's basically like driving in the foundation piles. We did three key things:

  1. Tech choices: even when the AI picks for you, lay the options out, understand the reasons, and then officially sign off. Being mainstream is a real plus for Vibe Coding.
  2. git init: a really important undo button and time machine.
  3. CLAUDE.md: the project constitution. Put in the rules the AI can't learn just by reading the code, and it gets loaded automatically in every conversation.

That's it for today. See you tomorrow.
