30 Days of Vibe Coding | Day 10: Building the First Feature with Plan Mode

Intro

SPEC.md, CLAUDE.md, the project environment — that's all pretty much done. Now we finally get to start actually building!

The first feature on the list is "add an expense." Since it's the very first feature in the whole project, we'll use it to show how to build things with Plan Mode.

Turning one feature from the SPEC into a prompt

First, let's look at the "Scope" section in SPEC.md:

Markdown
## 3. Scope

### In

- Add an expense
- Edit a recorded expense
- Delete a recorded expense
- Switch months to see that month's total spending and category breakdown
- Jump back to the current month in one tap
- See that month's transaction list

That's the list of features we "have to build." Before we start, make sure the AI is in plan mode on (remember? Just press Shift+Tab to switch) so it goes into planning mode.

Claude Code showing Plan Mode

Once you're in Plan Mode, we can take the first step: turning the feature list in SPEC.md into a prompt. One thing to keep in mind — in this post we're not asking the AI to build every feature in one go. We're only doing the first item on the "In" list, "Add an expense," and using it to show how Plan Mode works.

If that all sounds good, try typing this prompt into Claude Code:

Text
Following the first item on the "In" list in SPEC.md, "Add an expense," please write a development plan. List what this round will and won't do, and include acceptance criteria.

Yep, that's it.

"Don't I need to tell it about the fields and categories? Those are the basics of an expense tracker."

I know you might be wondering that, but you really don't. We already worked all of that out while writing SPEC.md.

Don't believe me? Look — the field rules are already written out in section 5 of SPEC.md:

Markdown
**Field rules**

| Field | Required | Default | Rule |
|---|---|---|---|
| Amount | Yes | Empty | Positive integer, must be > 0 |
| Category | Yes | None | Pick one of six, using buttons, not a dropdown |
| Date | Yes | Today | Native `<input type="date">` |
| Note | No | Empty | Single line of text, max 50 characters |

That's why I don't need to tell the AI...

  • What the fields are
  • What the categories are

We already spent time talking these through earlier, and SPEC.md has the full spec.

If you type all that out again in this prompt, you get two problems:

  1. You're writing the same thing twice, which wastes time
  2. The two might drift out of sync someday

That's why laying the groundwork up front matters so much. It's exactly why we spent the time getting SPEC.md, CLAUDE.md, and the project environment ready — so when it's time to build, we can get straight to the point.

After you hit send: it asks questions before giving you a plan

After you send that prompt, it might not hand you a plan right away. Instead, just like before, it may pop up multiple-choice questions and check things with you one at a time.

Multiple-choice questions

In my case, the questions were:

Bash
1. To review "Add an expense," you need to be able to see the result of adding one. Should this round also include a read-only transaction list and this month's total?
2. How far should src/composables/useRecords.js go in this round?

Asking how far this round's acceptance scope should go

When you hit questions like these, that's basically your cue to stop, flip through SPEC.md, and actually think about it. These are often things you didn't think of in the first place, which is exactly why we keep building in these check steps (and if there's anything you don't understand, just ask it — better than discovering the problem halfway through building). Every option can add complexity, difficulty, or plain workload to a feature. And the stuff you left out of your prompt doesn't magically disappear — it just gets asked at a different point in time. That's the value of Plan Mode.

Understanding how it wants to build the house

Next you should see the AI hand you a development plan. I really recommend you actually read it (we'll save this plan to a file in a bit, so hang on).

The plan the AI came up with

Please don't just see "Yes, and use auto mode" and click it without thinking.

The plan is a bit long, but I think it's worth taking some time to read. For example, it says things like...

  • Categories are hardcoded in src/constants/categories.js as the single source of truth.
  • src/composables/useRecords.js is the only place that touches localStorage.

Just those two lines might already wear you out. There's a lot of it, and it's packed with jargon, so it's totally normal for it to feel painful to read. But you can ask it to rewrite things into a "version that's easier to understand," and it'll break the plan down in a friendlier way. Say it's your first time seeing composable — you can type this into "Tell Claude what to change":

Text
What's a composable? Why do we need an extra useRecords.js file, and what is localStorage? Please explain it in a way that's easier to understand.

And you'll get a really detailed plain-language explanation:

The AI explaining what a composable is and what it's for

After reading the explanation, you should see that it didn't split things up randomly — it made those design decisions for real reasons.

And if... you understood it, you read it all, but you just don't have an opinion either way? Then go with the "recommended" option. "Recommended" is what it thinks is the best approach, so unless you can come up with a better reason, just go with it.

For now, though, don't click "Yes, and use auto mode" yet, because we've got a "controlled failure" exercise to do first.

Controlled failure exercise: bloat the scope on purpose, then hit the brakes

Next we're going to do a "controlled failure" exercise: deliberately bloat the plan, then pull it back.

Type this into "Tell Claude what to change":

Text
Back to the plan. Since we're building a form anyway, let's also add over-budget alerts and a way to record income.
Please update the plan, but don't execute it yet.

After sending it, again, don't rush to click "Yes, and use auto mode." Take a look at how the plan bloats first. You should also see the AI tell you something like this:

It clearly tells you these features aren't in scope this time

Markdown
### Out (explicitly excluded from v1)

| Not doing | Why |
|---|---|
| Recording income | It only answers "where did my money go," not assets and liabilities |
| Accounts / payment methods | Adding these leads straight to "balance per account," which the MVP can't handle |
| Budgets and over-budget alerts | First get people to actually record expenses, then talk about control |
| Month-over-month trend charts | Meaningless until there are a few months of data |
| Adding / deleting / renaming categories | A fixed built-in set is enough and saves a whole management screen |
| Accounts, cloud sync, multiple devices | Single user, single device |

Pretty interesting, right? The AI actually pushes back on our request, because it knows these features aren't in scope this time. And for those of us with itchy fingers who want to keep adding features, this is the perfect chance to practice hitting the brakes. As long as you don't accept it or allow it, you're fine.

Once you've seen how scope control works and how the plan bloats, press Esc or find the "Tell Claude what to change" box and type this:

Text
That was just a scope-control exercise. Budget alerts and income tracking are both on the "Out" list in section 3 of SPEC.md, so please remove all of them.

Go back to the original "Add an expense," list what this round will and won't do, and give me a new version of the plan.

It'll go back to the original plan, but you'll probably notice the AI adds a special note about it:

The AI specifically notes these features are out of scope

It's a tiny exercise, but it means a lot. Sometimes scope explosions aren't caused by the AI at all — it's the user suddenly thinking of something (just like a boss). The nice part here is that you hit the brakes before any work even started.

Approve it and watch it build

If the plan looks fine, click "Yes, and use auto mode" and let it run the plan. You'll see it start adding and changing files in your project until it's done (and if you'd rather see every change with your own eyes, picking manually approve is totally fine too — it's just slower).

When it's done, run npm run dev and open your browser. You should see the home page with a "+ Add" button, and after you add an expense, the bare-bones list below it will show the data.

After adding an expense, it shows up in the list

Keep the plan

Don't jump into reviewing yet. There's one thing a lot of people forget to do first:

If you don't save that plan, it's gone.

The plan was produced inside the conversation. Once you /clear, it gets wiped along with everything else on the desk. But it's actually really useful later on, for example...

  • When a bug shows up, you can pull it out and check whether the AI actually followed the plan.
  • A few months later, you can see why the files were split up the way they were.

So tell the AI:

Text
Please save the original text of that plan as docs/plans/01-add-expense.md. Don't rewrite or summarize it.

You really need that "don't rewrite or summarize it" part. Otherwise it'll helpfully condense the whole thing into three lines, and then there's no point in saving it (mine is at day10#docs/plans).

Once it's saved, your project will have a new folder:

Text
·········money-note/
└─ docs/
   └─ plans/
      └─ 01-add-expense.md

So... do you have to say this every single time? Of course not. A convention that keeps repeating like this is exactly what CLAUDE.md is for. Send it one more prompt:

Text
Please add the following dev rules to CLAUDE.md, and follow them in every conversation:

- Every time a Plan Mode plan is approved, the first thing to do is save the original plan text as docs/plans/NN-feature-name.md (NN starts at 01 and keeps counting up), and only start changing code after it's saved
- The plan file goes in the same commit as that feature's code

This is exactly the same move as on Day 9, when we added dev rules to CLAUDE.md. And it proves something:

CLAUDE.md isn't something you write once and never touch again. Whenever you find a convention worth keeping, add a line.

From now on, every round of feature work, it'll save the plan on its own. You won't have to tell it twice.

Reviewing the feature

Next up is review. You might be thinking...

"Wait, I have to spend time testing this myself?"

Not really. Your Plan Mode plan already listed the acceptance criteria for you — those 13 items in the plan. The first half maps to the acceptance criteria in section 7 of SPEC.md, and the second half are edge-case checks it added on its own. Every one of them is behavior you can check yourself just by opening the browser.

When the AI finishes, it'll tell you it already tested everything. Don't take its word for it just yet (why? You'll find out on Day 12). I still open it up and test by hand, especially these:

  • Tap "+" → enter an amount → tap a category → save — an expense is recorded in three steps
  • The one you just added shows up at the top of the list right away, and this month's total goes up
  • Change the date to last month and save — that one doesn't show up in this month's list

After adding an expense, it shows up in the list

Note

The acceptance criteria here are about "behavior," not "code." You don't need to check whether the code is written correctly — what matters is whether what it built meets the acceptance criteria.

If everything passes, the AI will ask whether you want to commit, because the "Wrap-up" section of the plan says:

Markdown
Once all 13 items above pass, commit once. Message format per CLAUDE.md:

Add expense: form, data layer, and transaction list

And that rule actually comes straight from the CLAUDE.md constitution:

Markdown
**Commit once each time a feature is finished and passes review.** Don't pile up several features into one commit — one commit maps to one reviewable feature, so you can go back when something breaks.

The commit rule in CLAUDE.md

Wrapping up

That's about it for today. Congrats on finishing your first feature.

You've probably noticed by now that even though Vibe Coding is an AI-driven way of building, it's not fully automatic. You still need to think, make judgment calls, and review, so the features you end up with actually match what you need.

Here's the rhythm of the whole process, so you can refer back to it when building other features:

  1. Your prompt just needs to point at which feature in SPEC.md you're building, then ask it to list what it will and won't do this round, with acceptance criteria. Don't keep feeding it new rules that could conflict with SPEC.md
  2. If it asks you questions, stop and think. Go back and check SPEC.md too — every option affects how much work comes later
  3. If there's anything in the plan you don't understand, just ask. Keep asking until you get it
  4. Once you have the plan, read it through properly, especially the data structure parts
  5. If you notice the scope growing — whether the AI suggested it or you thought of it on the spot — send it back and have it re-plan
  6. Save the plan as docs/plans/NN-feature-name.md, and put that convention in CLAUDE.md so you never have to ask again
  7. When reviewing, look at behavior, not code. Only commit after everything passes

Following these seven steps, you're already slowly building your own Vibe Coding workflow.

That's it for today. Congrats on your project's very first commit, and I hope this post helped you get your first feature done.
