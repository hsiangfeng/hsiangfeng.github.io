30 Days of Vibe Coding | Day 17: Making the UI Look Good (Part 2) — Locking In the Style with DESIGN.md

Intro

"Wait... why does the screen the AI changed this time look different from my original style?"

It's not just you. This happens all the time.

All the design style decisions we talked through (color palette, spacing, button hierarchy, copy tone) only exist in that one conversation's context. As soon as you close it or /clear to start a new chat, all of it disappears. Unless you specifically tell the AI to write those design decisions down in a document and lock them in, it'll keep improvising and guessing all over again.

So to solve that, in this post we're going to look at something called a design document (DESIGN.md).

Standing on the shoulders of giants: DESIGN.md

So why do we need this post and a design document at all? The main reason is that the AI's UI style is different every time, because design decisions usually only live in the current conversation's context. Once the conversation ends, they're gone.

Then whenever you ask the AI to build a new feature or component, it'll try to analyze and track down your previous design decisions and guess from reading the code, but it's hard for it to get right. That leads to all kinds of visual imbalance (inconsistent button colors, inconsistent spacing, inconsistent font sizes...). That's why we need a design document to lock in the style.

Inconsistent style

So here's the question: how do we actually fix this? Good news: Google has put together a standard format for design documents for us, called DESIGN.md.

It actually comes from Stitch, an AI design tool that can produce a UI from a one-sentence description. DESIGN.md is the design system format that grew out of Stitch, and in 2026 Google Labs open-sourced it on GitHub. The goal is to let every AI tool (Claude Code, Cursor, Copilot...) understand your design system using the same format.

Note

You might notice that the official project and npm package use lowercase design.md (you'll see it in the commands coming up). To keep things consistent and easy to read, I'll just call it DESIGN.md in uppercase throughout this post.

So how does DESIGN.md solve the problem? Let me give you a scenario. Say you ask the AI to make a blue button. The AI might do this...

  • First time: #3B82F6
  • Second time: #2563EB
  • Third time: bg-blue-500

Three different color codes

They're all blue, but... they're still slightly different. Those subtle differences make the screen feel unbalanced or even a bit weird, not to mention the problems once it's in a real product.

"Can't I just write these rules in CLAUDE.md? Isn't CLAUDE.md the supreme constitution?"

I bet that's the first thing that popped into your head. It's definitely one way to do it, but the DESIGN.md approach is better, because it splits design decisions into two layers:

  • YAML front matter: holds the exact design tokens (color codes, fonts, spacing, corner radius, components). This part is for machines to read precisely.
  • Markdown body: holds the design reasoning: why this color, when to use it, when it's off-limits. This part is for people (and the AI) to read.

That way, the AI doesn't just know "the primary color is #245C4A." It also knows "where this green is allowed to be used," and even what the overall design philosophy is. That cuts way down on the chances of it using the wrong color.

Let it hand in its own design doc

So how do we actually write this DESIGN.md? I'm sure a lot of people are wondering. And the answer is: have the AI put it together and write the DESIGN.md itself!

Remember the last line of yesterday's prompt, "When you're done, tell me which design decisions you made and why"? That line was actually laying the groundwork for today. The AI is the one that made the most design decisions during the whole makeover, so it knows them best. It's the perfect one to write this document.

It's simple. Just type the following prompt (manual mode on or accept edits on is all you need here, no need for Plan Mode):

Text
Please run `npx @google/design.md spec` to learn the format DESIGN.md requires, then put this project's current design decisions together into a spec-compliant DESIGN.md in the root directory. The content must be based on the actual code (check the color codes against the tokens in src/style.css).

In the Markdown body, besides the officially recommended sections, please add an extra section called "Responsive and accessibility review" that includes review criteria like 375px / 768px and buttons being at least 44px tall.

If CLAUDE.md already has any styling-related rules, move them into DESIGN.md as well. Don't keep a copy in both places.

From now on, any UI-related change must follow the DESIGN.md spec, with no more changing things from memory. So please add this line at the top of CLAUDE.md:
See @SPEC.md for the spec and @DESIGN.md for the design guidelines. All UI-related changes must follow the design guidelines.

I bet you're full of question marks right now. Don't worry, let me explain three parts of it:

  • The npx @google/design.md spec in the first paragraph: This command outputs the format spec for "what a standard DESIGN.md should look like." So you're basically asking the AI to read the DESIGN.md spec first before starting. That way the file it writes actually follows the standard, instead of being something it made up.
  • "Move them into DESIGN.md as well" in the third paragraph: This is to avoid having one rule in two places. If you don't do this, there's a good chance you'll hit "changed A, forgot to change B," and you end up with documents fighting each other. So take the chance to clean it up now, and let the design guidelines live in just one place: DESIGN.md.
  • The @SPEC.md / @DESIGN.md in the last paragraph: The core point of this line is to make the AI automatically read the design guidelines (DESIGN.md) every time it starts a new conversation. As for the @... I'll explain that a bit later.

Here's a short excerpt of the DESIGN.md for reference. For the full file, check out the DESIGN.md in the project:

Markdown
············---
version: alpha
name: Money Note Warm Paper Ledger
description: Design system for a single-user expense tracker. Ink on paper, ledger column lines, a double underline under totals, numbers first, not a blue-and-white admin dashboard.
colors:
  # === Base colors ===
  paper: "#F3EFE7"
  card: "#FFFDF8"
  # === Ink colors ===
  ink: "#1F2925"
  ink-soft: "#56625C"

... (a bunch skipped)

# Money Note Design Guidelines

See [SPEC.md](./SPEC.md) for the implementation spec. This document only covers what the screens look like: color palette, type scale, spacing, component states, and review criteria.

**The single source of truth is the tokens in the code.** The values in the YAML front matter map one-to-one to the `@theme` block in `src/style.css` and to `src/constants/categories.js`. Change one side, and you have to change the other.

## Overview

Money Note is a personal expense tracker. The core scenario is "right after spending money, standing outside a convenience store, logging it on your phone." So the whole visual design serves just one thing: **letting the numbers be read the fastest and entered the fastest.**

The visual direction is a **warm-toned paper ledger**, not an admin interface. The screens should read like an open handwritten ledger: cream paper, dark ink, a horizontal ruled line for each entry, a vertical line in the amount column separating money from text, and the accounting-style double underline under the monthly total.

The three kinds of ledger lines carry information on their own (one row per entry, money and text in separate columns, a single line for subtotals and a double line for totals), so using them as the layout skeleton means no extra decoration is needed. **Hierarchy always comes from line weight and the two layers of paper/card background, not from shadows, rounded corners, or the number of colors.**

The mood should be quiet, trustworthy, and easy on the eyes, closer to a "tool" than an "app." No gradients, glass effects, emoji icons, over-the-top shadows, or walls of colorful tags. The most eye-catching thing on the screen is always the monthly total, and everything else steps back behind it.

DESIGN.md contents

Pretty handy, right? Just have the AI put it together, and you don't have to figure out the YAML format or how to write the Markdown sections yourself.

Design docs have a linter too

What do I mean by "design docs have a linter too"? In short, a linter is a tool that "checks" a specific format. ESLint, Stylelint, and Markdownlint are all examples. And DESIGN.md? Of course it has its own linter too.

So why bring this up? Because unless you're familiar with DESIGN.md, it's really hard to spot by eye whether the AI got the format right. Luckily, the official project provides a linter to help with that, so you can type the following prompt and have the AI check whether your DESIGN.md has any problems:

Text
Please run `npx @google/design.md lint DESIGN.md` to check whether DESIGN.md follows the DESIGN.md spec, and report the results back to me.

Lint results

So what does lint actually check? Mainly these:

  • Whether the YAML structure is correct, whether colors includes the required primary, and whether any recommended sections are missing
  • Whether any token references are broken (like {colors.primery} missing an "a," or using a property the spec doesn't recognize)
  • Whether there are orphan tokens that are "defined but never used"
  • Whether it passes WCAG AA contrast

Super handy, right?

Note

If you're on Windows and DESIGN.md doesn't seem to respond, .md might be getting swallowed by the file association. Try npx -p @google/design.md designmd lint DESIGN.md instead.

Adding it to the constitution

Don't think we're done just because we covered all that. Even with a DESIGN.md design document keeping things in check, you have to make sure the AI automatically reads it every time a new conversation starts. Otherwise it'll still forget.

So we need to add this line to CLAUDE.md:

markdown
See @SPEC.md for the spec and @DESIGN.md for the design guidelines. Any UI-related change must follow the DESIGN.md guidelines.

Of course, you can also just hand this line to the AI and have it add it for you, so you don't have to edit the file by hand.

Text
Please add this line at the top of CLAUDE.md:
See @SPEC.md for the spec and @DESIGN.md for the design guidelines. Any UI-related change must follow the DESIGN.md guidelines.

Next, you're probably curious what @ actually is. We've used similar syntax before, like "please read @SPEC.md," but it's worth pointing out that it works a little differently depending on where you use it:

  • @ in a conversation: The file only gets read for "this one conversation."
  • @ inside CLAUDE.md: This is CLAUDE.md's import syntax (pull this file in), so the file gets loaded automatically every time you start a new conversation.

With that in mind, let's look at where things stand now. All the core documents are pretty much in place. Did you notice? Here's the role each one plays:

  • SPEC.md: handles "what to build"
  • CLAUDE.md: handles "how to build it"
  • DESIGN.md: handles "what it looks like"

And none of these files disappear when a conversation ends. Every time you start a new conversation, CLAUDE.md automatically pulls in SPEC.md and DESIGN.md, so the spec and design decisions don't get forgotten.

So does it actually lock it in?

DESIGN.md is written, and CLAUDE.md now has @DESIGN.md. But is the style really locked in? I think that's what everyone's wondering, so let's run an experiment and see whether the DESIGN.md guidelines actually keep the style in place.

First, start a brand-new conversation (type /clear), then type the following prompt (don't forget to switch to Plan Mode):

Text
Above the "Add an expense" and "Expense list" headings, please add small section labels: "New entry" and "Recent entries," respectively.

You should then see in the AI's thinking that it really did refer to DESIGN.md. That means the style lock we were hoping for is working.

The AI's thinking process

Wrapping up

That's about it for today. Here are the key points, all wrapped up:

  • UI style evaporates along with the conversation. The fix is to write your design decisions into a DESIGN.md, and you don't have to invent the format yourself. Just use the design.md spec Google Labs open-sourced: YAML holds the exact design tokens, and Markdown holds the design reasoning.
  • Once @DESIGN.md is hooked into CLAUDE.md, every conversation automatically loads the three core documents:
    • SPEC.md handles what to build.
    • CLAUDE.md handles how to build it.
    • DESIGN.md handles what it looks like.

If that all makes sense, see you in the next one.
