30 Days of Vibe Coding | Day 8: Turning Ideas into a Spec — Writing SPEC.md with AI

Intro

Starting today, we're pretty much getting ready to build. We've already sorted out the AI concepts and the little details of using Claude Code, so naturally it's time to move into the implementation phase.

But! Even though we're heading into implementation, we still won't write a single line of code today. The first step of Vibe Coding isn't telling the AI to write code. It's learning to explain what you actually want.

By getting your "requirements" clear, you can turn a fuzzy idea in your head into a concrete spec document, SPEC.md. But how to get your requirements clear is a whole different story. So this post covers some techniques to squeeze that fuzzy idea into a concrete SPEC.md as much as possible, so the AI doesn't fill in the blanks on its own and hand you something that's heading who-knows-where.

AI amplifies your vagueness

First, there's one thing I think you need to accept:

AI is super convenient, but if you don't make your requirements clear, different models will fill in the gaps in noticeably different ways.

Note

Models differ in training data, training methods, model size, and parameters, so they'll interpret the same prompt differently. Even the same model can behave differently at different points in time.

Let's use the small expense tracker we'll be building later as an example (the project folder will be called money-note).

Say you just tell the AI "build me an expense tracker app." Have you thought about how the AI will interpret that?

  • Does it need money transfers?
  • Does it need cloud sharing?
  • Where should the data be stored?
  • Does it need login?
  • Does it need to store user data?

When the AI runs into requirements it's unsure about, it'll pop up a multiple-choice screen like this and ask you:

The AI popping up multiple-choice questions to clarify requirements

Those questions showing up means the AI finds the request really unclear. So the AI tells itself, "I think I should ask the user what they need," and throws these options at you to pick from.

The more room you leave it to guess, the further the final product will drift from what you imagined. You might even get features you never wanted. That's why we need to make the requirements clear first, so the AI doesn't fill in the blanks on its own.

It's just like talking to an engineer. If all you say is "build me an expense tracker app," the engineer is going to ask you a ton of questions too, because they don't know what you need either.

Let the AI guide you through building the spec

After all that, have you ever wondered what a "spec" actually is?

In short, a spec is a product specification document. It lays out in detail the features you want, the features you don't want, and how to check whether the project counts as done.

But here's the problem: for a total newbie like me, how are you even supposed to write one? We don't have the background, and we're not Product Managers either, so sorting out requirements is definitely going to feel like a struggle.

So this is where we lean on working with AI. We'll have it help us turn the fuzzy idea in our heads into a concrete SPEC.md.

First, open your terminal and run these commands to create the project folder (same as the claude-playground one from before):

Bash
mkdir money-note # create the project folder
cd money-note # go into the project folder
claude # start Claude Code

Once you're in Claude Code (don't forget to use Shift+Tab to switch to manual mode, the default mode), we'll use a style of asking I call the "interview-style prompt". This Prompt has three key points:

  1. Tell the AI clearly not to write any code yet, so it doesn't get overeager and start building.
  2. Have it ask only one question at a time, so it doesn't throw ten questions at you at once and stump you. Trust me, this really is better (speaking from experience, sigh...).
  3. Once the AI thinks things are specific enough, have it organize everything into SPEC.md.

So now, copy the Prompt below, paste it into Claude Code's input box, and hit Enter:

Text
I want to build a small expense tracking tool. Don't write any code yet.
Act as my product consultant and ask me one question at a time to clarify the requirements.
Once you think it's specific enough, tell me it's ready to be organized into SPEC.md and ask me to confirm.

After sending the interview-style prompt, it asks back about the requirements

Note

Remember that AI is random. The content and options on your screen may look different from mine, but they'll generally revolve around three areas: users, feature scope, and data storage.

What follows is basically a long round of interrogation. The scope will probably cover things like:

  • What's the motivation? (I want to log expenses quickly and always know how much I've spent this month)
  • Who's using it? (Just me, single user)
  • Income or expenses? (I answered "just expenses" at the time. Remember that answer, because on Day 10 it comes back to bite me)
  • Which fields do you need? (Amount, category, date, note)
  • Where should the data be stored? Does it need to sync across devices? (Local is fine, no sync needed)
  • What stats do you want to see? (How much I spent this month, and the share by category)

...and so on.

During this process, you'll probably notice some questions you'd never even thought about. That's exactly where the value of the "interview style" comes in.

An interview-style Prompt drags out all those half-formed decisions in your head one by one, and in the end you get a complete requirements summary. If it looks fine to you, you can ask it to organize everything into SPEC.md and save it.

The requirements summary it put together

At this point you're probably curious: what's the difference between an "interview-style Prompt" and Plan Mode? Here's the difference:

  • Plan Mode: it's geared toward starting work once the plan is done. It produces an implementation plan (which files to touch, what steps to take), then asks whether you want to go ahead. It'll ask you questions when things are fuzzy too, but the point of those questions is always what it needs "to lock down the plan and start implementing."
  • Interview-style Prompt: it's geared toward clarifying requirements. The goal isn't to start building. It mainly produces a requirements spec, figuring out the what (what to build) first. The how (how to build it) is Plan Mode's job later. And you control the pace of the questions, since you told it to dig one question at a time instead of letting it decide when it's asked enough.

So what does the actual output look like? Here's the SPEC.md I ended up with:

  • GitHub link: day-8#SPEC.md

There are a couple of important parts in this SPEC.md: "explicitly not doing" and "features to build." These two draw the boundaries of the scope, and they're really important. Without them, there's a high chance your scope explodes and the product never gets to launch first.

Note

Scope explosion here means building whatever pops into your head, until the project dies before the first version is even out. What a product needs most is to grab that "first-mover advantage".

One last reminder here:

A spec isn't holy scripture, and it's not set in stone.

It's a living document. As your understanding of the project gets clearer during development, the doc gets updated too. But it should basically stay within the agreed scope. If you want to add or remove features, put them under future expansion first, and update SPEC.md at the same time so the doc stays in sync with reality.

Run a scope check before you start building

Next, don't rush to hand this SPEC.md to the AI to build. Right now, this SPEC.md is just what came out of a Q&A between you and the AI, and during that process you were both in a "let's wrap this up quickly" mood. If you implement straight from it, it's really easy to miss things. So we'll ask the AI for one more "scope check."

Type /clear or /new to wipe the earlier conversation, and swap the AI's "product consultant" hat for an "inspector" hat. From a third-party angle, have it go through the spec and check three things:

Text
Read SPEC.md, and don't change any files yet. Check three things for me:

1. Is any item in the "to build" list too vague to be checked?
2. Do any items in "to build" and "not building" contradict or overlap each other?
3. Is there any feature mentioned in the text that doesn't appear in the "to build" list?

Only report the results. Don't touch any files.

Scope check

You'll see it catches a bunch of issues that haven't been decided yet. Some you can probably understand (hopefully?), like this one:

Markdown
SPEC.md:112 says "no limit on how far back or forward you can switch," but there's no "back to this month" entry on screen. If a user accidentally switches to 2019, they'd have to press ▶ 80-something times to get back. Either add a "This month" button, or state in the spec that this trade-off is accepted.

For me, just adding a "This month" button solves it:

Text
Add a "Back to this month" button to the month switcher, and add it to the "to build" list and the acceptance criteria.

This is exactly the kind of thing neither you nor the AI happened to think of, and that's why you do a scope check. You were both in a hurry to wrap up, so a lot of details slipped by.

Fixes after the scope check

Okay, that one's handled. But... what if some of them you just don't understand? What then? For example:

Markdown
The sample data in SPEC.md:54 contradicts itself: date: "2026-08-07", but createdAt: 1754534400000 converts to 2025-08-07. That's a year off. Samples like this often get copied straight into test data or seeds.

It's fine if you don't understand it. Just don't skip it and pretend you didn't see it. You can ask the AI to explain:

Text
Also, I don't understand this one: "The sample data in SPEC.md:54 contradicts itself: date: "2026-08-07", but createdAt: 1754534400000 converts to 2025-08-07. That's a year off." Can you explain it in plain language and suggest a correct example?

It'll explain in plain language that createdAt is a "timestamp" (one way computers record time), and that the number in the sample converts back to 2025, a year off from the 2026 above. Then it'll give you a corrected value.

Plain-language explanation

At this point, let's assume everything checks out. So we lock it in with the AI like this:

Text
Update SPEC.md based on these conclusions, and don't touch anything else.

Finally, add a "Decision Log" section at the end of the doc listing the decisions we made this time.

Decision log

Trust me, keeping a decision log matters a lot. A few days from now you'll definitely forget why you decided something, and then you can just flip to this section instead of thinking it all through again.

From here on, it's your turn. Try going back and forth with the AI to clarify things and get a feel for how powerful the "interview-style Prompt" is, until you feel every feature in SPEC.md can be checked, nothing contradicts, and nothing's missing.

Later, when it's time to build your own project, the process is the same:

  • Make a call on each issue the check catches, one by one
  • Ask the AI to update SPEC.md, then run the check prompt above again after the update

Only when all three questions come back with "none" is the spec final.

I've drawn the whole flow as a chart for reference:

Flowchart

Here's some homework for you:

  • Follow the flow above and create a SPEC.md that has three sections: "to build / not building / acceptance."
  • Things like account login, budget alerts, and cloud sync must be explicitly listed under "not building."

This whole process is really about forcing you to think things through. Otherwise, once you actually start building, all those fuzzy areas you didn't think through come back one by one to collect their debt. That's how scope explosions happen (and it's also why engineers are always complaining that PMs never get the requirements clear).

Wrap up

Okay, that's about time, so let's wrap up.

We didn't write a single line of code today, but we were actually working on the most important thing: "turning ideas into a spec." That's laying the foundation.

Going from knowing nothing, to having a fuzzy idea, to having a concrete spec doc used to take days in the past, sometimes even pulling in other people to help run requirements interviews. Now, with AI helping out, we can squeeze a fuzzy idea into a concrete spec in a short amount of time.
