30 Days of Vibe Coding | Day 5: Permissions and Plan Mode — Stop Hitting Yes on Everything

Intro

After yesterday's first little exercise, the AI probably asked you a few questions, and at least once it asked "Can I change this?" — and you decided whether to hit "Yes" and let it edit the file.

But... use it long enough and you'll notice those confirmation prompts show up a lot. Then human nature kicks in, you start hitting Yes on autopilot, all the way to the end, and then it hits you: "Oh no, I just broke the whole project!"

So today I want to properly explain this "Permission" mechanism — which actions it'll ask you about and which ones it won't — so you can avoid getting nagged to death while still keeping your project safe from random edits.

The AI's access control

Remember this screenshot from yesterday?

The result of opening index.html in the browser after Claude Code's changes

Notice that even though we were the ones who asked the AI to open the browser, it still asked: "Is it OK if I open the browser?"

Weird, right? We literally sent this prompt ourselves:

Text
Please open index.html for me. I want to see the result in my browser.

So why is it still asking? That's what this chapter is about: the "Permission" mechanism.

This isn't unique to Claude Code — other AI Agent tools have something similar. It decides which actions are allowed and which ones need your confirmation first, and it's not random.

How permissions basically work

The core idea is actually pretty simple. It comes down to whether an action leaves a mark on your computer. There are basically two kinds of actions:

  • Actions that leave a mark (a trace)
  • Actions that don't leave a mark

What does that mean? Imagine that before doing anything, the AI asks itself one question:

"If I do this, will it leave a mark on this computer? If so, I need to stop and ask the user whether that's OK."

On the flip side, if it's just looking at / reading files or searching, it mostly won't ask you.

But! Editing files, creating new files, that kind of thing — anything that leaves a mark on your computer — by default it'll stop and let you know what it's about to do.

When Permission asks you

OK, I know that might sound a bit wordy, so just remember this one line:

Looking doesn't need permission. Touching does.

Claude Code asking for permission

Once you get this big-picture idea of access control, you'll see that the AI asking isn't it being annoying. It's doing something that might leave a mark on your computer, so it stops to ask you:

"Can I do this?"

Can I do this?

Note

One thing to watch out for: just because a command didn't trigger a permission prompt once doesn't mean it'll never ask, and it doesn't mean it's guaranteed to be safe either. That mostly depends on your current mode and the rules you've approved before.

The six permission modes

Now that you've got the basic idea of access control, let's go a bit deeper into permission modes.

First, a quick experiment. Just like yesterday, go into the claude-playground folder and launch Claude Code. Then press Shift+Tab a few times. You'll see the mode near the input box cycle through these:

  1. manual mode on
  2. accept edits on
  3. plan mode on
  4. auto mode on (not everyone has this one — I'll explain in a sec)

Pressing Shift+Tab to cycle through permission modes

These are the permission modes you'll use day to day. (Remember to switch back to manual mode on.)

Here's a fun little detail: if you go dig through the official docs (Permission modes (official docs)), you'll notice the names don't quite match what's on your screen. For example, the docs' default mode is actually what shows up as manual mode on. So I've matched them up for you below:

On-screen labelName in the docsBehavior
manual mode ondefaultAsks every time before touching anything
accept edits onacceptEditsCommon file edits and filesystem commands go through automatically; everything else still asks
plan mode onplanResearch mode: it researches first, then asks whether you'll let it run the plan
auto mode onautoBasically allows everything, but with some safety checks running behind the scenes, so it asks way less often

I want to call out accept edits on (acceptEdits) specifically. In this mode, common file edits and filesystem commands get auto-approved, for example:

  • Creating folders (mkdir)
  • Moving things (mv)
  • Deleting things (rm)

Commands like these become approved by default, so it doesn't ask "Is this OK?" every time. But you should still get in the habit of checking what the AI is about to do, because I've personally had an AI move my entire project folder somewhere else, and for a while I couldn't find anything.

Now a bit about the official docs. They list six permission modes in total. On top of the four above, there are two more:

  • dontAsk: In this mode, anything that would normally trigger a permission prompt just gets denied. It only runs actions you've pre-approved. This is great for automation scripts (where a program runs the AI Agent by itself), which is why it doesn't show up in the Shift+Tab cycle.
  • bypassPermissions: It doesn't ask you anything and just lets everything through. I really don't recommend using this casually. It's basically meant for sandboxes (an environment isolated from your actual computer). If you turn it on carelessly on your own machine, it's like handing over your house keys and leaving the front door wide open. It doesn't show up in the Shift+Tab cycle either — you have to add a flag to the launch command to get it.

So the extra dontAsk and bypassPermissions modes only show up when you pass a flag at launch; you can't switch to them normally. Here's how you'd launch them, just for reference (please don't use these casually):

Bash
# Launch in dontAsk mode
claude --permission-mode dontAsk
# Launch in bypassPermissions mode
claude --permission-mode bypassPermissions

If you do use bypassPermissions, make absolutely sure you're in an isolated environment (a Sandbox). Otherwise one day you'll be the main character of a disaster story on social media.

Plan Mode

I highly recommend Plan Mode — it's also the mode I personally use the most. The idea is: plan first, think first, and only then decide whether to actually do it.

With Plan Mode on, the AI becomes read-only. It can read your project and do research, but it can't change a single file.

Enough talk, let's actually try it. Remember where we left off with yesterday's practice file? You should have ended on this request:

The button text should be "Change background color", not "Click me".

If you can't find it or don't have it, you can grab the practice files from GitHub #day5.

Today we're going to use Plan Mode to add some stuff to this practice page and turn it into a simple personal profile page. The profile needs three sections added at once, which makes it perfect for practicing Plan Mode.

So launch claude to get into Claude Code, and press Shift+Tab in the input box to switch to plan mode.

Pressing Shift+Tab to switch to plan mode

Once you've confirmed it says plan mode on, copy and paste this into the input box:

Text
I want to add three sections to index.html: an About Me section, a Skills list, and Contact info.
Keep the original heading and the "Change background color" button.
Note

So the AI isn't working with less information than you, remember to first ask it What's in this folder? What's inside index.html?, and then send the text above. That way it knows what you actually want.

There's a pretty good chance you'll see a screen like this next:

The AI asking clarifying questions

Why is it asking these? Because the task (the prompt) we gave it has gaps, so it gives you multiple-choice questions to cut down the chances of it making changes you didn't expect.

Next, the AI will throw a big wall of information at you. This is the heart of Plan Mode: it researches your project first and then hands you a plan, and you decide whether to let it go ahead. Here's the full plan I got, for reference:

Markdown
Ready to code?

Here is Claude's plan:
Add three sections to index.html

Context

day-5/claude-playground/index.html is currently only 17 lines: an <h1>, a line saying "Nothing here yet.", an external link, and a button that randomly changes the background color. It's a vibe coding practice page and doesn't have real content yet.

This change adds three sections — About Me, Skills, and Contact — while keeping the original heading and the background color button. The content will use neutral placeholder text (no made-up personal details) for Ray to replace later. It'll also add a small bit of inline CSS so the page stays readable with three more sections.

Stick with the current single-file style: no external fonts, no dark mode, no splitting into multiple files.

Files to change

Just one: day-5/claude-playground/index.html

Approach

1. What stays untouched

- <h1>Hello，這是我的 Vibe Coding 練習頁</h1> — text unchanged
- The button <button type="button" id="bgBtn">隨機換背景色</button> and the <script> at the bottom — completely untouched, including id="bgBtn"

2. Two things that will change (please confirm when approving)

- Line 8, "Nothing here yet.": this won't be true once the three sections are added, so I suggest replacing it with a short intro line (placeholder text). If you'd like to keep it, just say so.
- Line 9, the israynotarray.com link: I suggest moving it into the Contact section so it's not stuck awkwardly between the heading and the sections. The link itself and target="_blank" stay, and I'll add rel="noopener noreferrer" while I'm at it.

3. New structure

Below the heading and above the button, add a <main> containing three <section>s, each starting with an <h2>:

┌──────────┬───────────────────────┬──────────────────────────────────────────────────────────────┐
│ Section  │ Markup                │ Sample content                                               │
├──────────┼───────────────────────┼──────────────────────────────────────────────────────────────┤
│ About Me │ <h2> + one or two <p> │ A neutral line like "I'm OOO, and I mainly do frontend..."   │
├──────────┼───────────────────────┼──────────────────────────────────────────────────────────────┤
│ Skills   │ <h2> + <ul><li>       │ HTML / CSS / JavaScript / Git, etc., each with a short note  │
├──────────┼───────────────────────┼──────────────────────────────────────────────────────────────┤
│ Contact  │ <h2> + <ul><li>       │ Email (mailto: placeholder), blog link, one other social     │
└──────────┴───────────────────────┴──────────────────────────────────────────────────────────────┘

Put a short HTML comment saying "edit here" next to each placeholder value so it's easy to replace later.

Also add <meta name="viewport" content="width=device-width, initial-scale=1"> to the <head> — once there's a max-width on the layout, phones will zoom it out without this line.

4. CSS scope

One inline <style> block in the <head>, doing only four things:

- body: system font stack, line-height: 1.7, max-width around 40rem centered, padding
- section: vertical spacing between sections
- ul: spacing between list items
- button: a bit of padding and cursor: pointer

Key constraint: don't set a background on anything other than body. The button's JS writes the color into document.body.style.backgroundColor (an inline style), so as long as section / main don't have their own background, the color change will still show through the whole page. body itself can have a default background; the inline style has higher priority, so they won't conflict.

Not adding: external fonts, dark mode, favicon, animations, CSS variables.

Verification

1. Open day-5/claude-playground/index.html directly in the browser
2. Confirm all three sections are there, the heading text wasn't changed, and the layout is readable on both desktop and narrow windows
3. Click "Random background color" a few times — the whole page background should change, with no white blocks from the sections covering it
4. Open the DevTools Console and confirm there are no errors (getElementById('bgBtn') must not become null)

The plan generated by Plan Mode, with approval options at the bottom

Once the plan is out, you'll see some options below it:

  • Yes, and use auto mode (approve it and switch to auto mode)
  • Yes, manually approve edits (approve it and switch to manual mode)
  • Tell Claude what to change (don't approve it; tell Claude Code what to change)

The wording may differ slightly depending on your version — as long as the meaning matches, you're fine. But for now, don't pick Yes, and use auto mode. Press Esc to leave the menu instead, since we're just getting a feel for how Plan Mode works.

With that done, let's go over a few key points about Plan Mode. When you're in Plan Mode, I strongly recommend actually reading the plan. Things like:

  • Which files is it planning to touch or change? (Does it go beyond what you expected?)
  • Does the order of the steps make sense?

If you're worried you won't understand what the AI is saying (tons of technical jargon, for example), you can use "Tell Claude what to change" to ask it to explain things more simply. That's one of the handy tricks for actually understanding what it's about to do.

That way you won't end up with that "I have no idea what it just did" feeling. The whole point of this mode is to let you see the plan first, then decide whether to go ahead.

A controlled failure: revise the Plan Mode plan

Now that you know the basics, let's try the other key part of Plan Mode: revising the plan.

Right now we've pressed Esc, left the menu, and we're back at the input box. But the plan we just got is still sitting there in the conversation.

The Plan Mode plan still in the conversation

Let's try revising it. Copy and paste this into the input box:

Text
Don't run this plan yet. Revise it and give it to me again:

1. Don't include email in the contact info. Use GitHub and Threads links instead.
2. Only change index.html. Don't add any packages or other files.
3. Make my name a link to "https://israynotarray.com/" with target="_blank".

Also, list "What I won't do" at the very top of the new plan.

You'll get another big chunk of plan back:

Markdown
Ready to code?

Here is Claude's plan:

Add three sections to index.html (revised)

What I won't do

- No new files: no style.css, script.js, or README, and no touching day-4 or any other folder
- No packages: no npm, no build tools, no package.json
- No external resources: no Google Fonts, no CDN, no favicon, no images
- No email: contact info only has GitHub and Threads links, no mailto:
- No touching the button or its JS: id="bgBtn" and the background color <script> stay exactly as they are
- No changes to the <h1> heading text
- No extra design: no dark mode, CSS variables, animations, or responsive breakpoints

Context

day-5/claude-playground/index.html is currently 17 lines: an <h1>, a line saying "Nothing here yet.", an external link, and a button that randomly changes the background color.

This change adds three sections — About Me, Skills, and Contact — while keeping the original heading and button. The content uses neutral placeholder text (no made-up personal details) to be replaced later, plus a small bit of inline CSS to keep the layout readable. All changes stay within the same file.

The revised Plan Mode plan

This time, the plan clearly includes a few things:

  • What it won't do: no email, no new packages, only one file touched
  • What it will do: three sections, keep the original heading and button, and the button still works

If anything's missing or there's something extra, you can use "Tell Claude what to change" to ask for revisions, and keep sending it back until it matches exactly what you want. That process is basically forcing you to build the habit of "read the plan first, then act".

Once the plan is revised to your satisfaction, this is when you can actually hit "Yes, manually approve edits".

Notice I said "Yes, manually approve edits", not "Yes, and use auto mode". That's because I want every step the AI takes to pass in front of your eyes, so it doesn't do something you didn't want. Once you approve, it leaves Plan Mode and gets to work.

When it's done, don't forget to verify the result. For example:

  • No weird extra files showed up.
  • Open it in the browser and check that the three sections and the two social links are all there.
  • Click the "Change background color" button and make sure the original feature still works.

That last one is especially important. After the AI adds or changes a feature, we have to make sure the old features weren't broken — and this is a good chance to start building that habit.

Note

Personally, I mostly reach for Plan Mode when a change touches multiple files (roughly two or more), when I'm working on a project I'm not familiar with, or when I have no idea how to approach something. It also saves quite a bit on cost (we'll cover Tokens in a later chapter).

Wrapping up

As usual, let's sum up today's key points:

  • The basic access control idea comes down to "looking doesn't need permission, touching does".
  • The core modes you'll use:
    • manual mode on (default): asks every time before doing anything
    • accept edits on (acceptEdits): common file edits and filesystem commands go through automatically; everything else still asks
    • plan mode on (plan): researches first, then asks whether you'll let it run the plan
    • auto mode on (auto): allows everything, but with safety checks running behind the scenes
  • Use Shift+Tab to switch modes
  • If you don't like the plan, send it back. Planning things out before doing them works a lot better.

Hopefully this gave you a better understanding of Permissions and Plan Mode.
