30 Days of Vibe Coding | Day 24: Refactoring to Pay Down Tech Debt

Intro

Wait... AI-written code can have tech debt too?

Of course! Even AI racks up tech debt, okay?

We've used a bunch of ways to avoid going into debt so far — keeping it to one feature at a time as much as possible, reviewing and committing as soon as something's done, even writing unit tests. But there's still some tech debt you just can't avoid. So in this post, we're going to talk about AI tech debt.

So, what is tech debt?

Some of you might not be sure what tech debt actually is, so let me spend a bit of time explaining it first.

Tech debt... in short, it's what you get from rushing.

What do I mean? Usually when we're building a project, we want to grab the market, hit a deadline, or just get the feature out first. So we might write code that isn't clean enough or consistent enough, skip proper testing, leave the docs incomplete, and so on. All of that is quality we temporarily sacrifice to ship fast.

And that sacrificed quality is what we call "tech debt."

Here's an everyday example. Say we buy a house and move everything in really fast, but all the cardboard boxes just get tossed in a corner. As long as you can start living there and using the place, who cares, right? But a while later, you find out that finding one charging cable means digging through three to five boxes, because when you moved in, you never really thought about where anything should go.

Code works the same way. The same code, the same logic in two places, so you keep changing file A and forgetting file B. Or the docs say one thing and the code does another. None of it breaks anything right now, but once you need to maintain or extend the project, you start paying interest. That's the idea behind tech debt.

So why bring this up? Because the Vibe Coding way of building actually makes it easy to pile up a ton of tech debt.

With traditional fast development, each round might only leave behind a little crap (as in bad code). But Vibe Coding doesn't just speed up development — it speeds up the crap too.

Take stock first, don't rush into refactoring

Cleaning up tech debt is what we call "refactoring." The definition of refactoring is "change the structure, not the behavior." In other words, the point of refactoring is to make the code cleaner, more consistent, and easier to maintain, without changing what the program does. That's also why I planned a whole testing day earlier in the series.

Refactoring can make your code cleaner, more consistent, and easier to maintain, sure — but at the end of the day you're still changing code. There's no guarantee the result after your changes matches what you had before, which is why tests are often called a "safety net."

So how do we get started? It really comes down to one thing: "taking inventory."

Open up our practice project again, go into Claude Code, and type /clear in the chat box to make sure the conversation is wiped. Then press Shift+Tab to switch to Plan Mode (you're good once you see plan mode on), and type:

Text
Please take inventory of this project's tech debt:

- Duplicated logic
- Oversized components (more than 300 lines)
- Inconsistent patterns

Plus anywhere the code doesn't match CLAUDE.md or the existing docs.

This time I only want the list, no change plan. Give each item a severity and a recommendation.

Next you should see a list of suggested changes, and that's the tech debt list the AI pulled together for us.

But you'll notice I'm using Plan Mode for the inventory instead of just asking the AI to do it in Accept Edits Mode. Why?

Think of the AI as a really overeager helper. It's taking inventory... taking inventory... and then for whatever reason it just starts fixing things while it's at it. Next thing you know, there's a pile of Diffs (change records), and you don't have time to decide which changes should happen and which shouldn't. That's why I do the inventory in Plan Mode, so you can read the list first and then decide whether to change anything.

I bet you're thinking: "Can't I just write 'don't change anything yet' in the prompt?"

Honestly, that's not wrong. But if its Context blows up, it'll forget that eventually anyway, which is why I recommend doing the inventory in Plan Mode.

The tech debt list the AI came up with

Pretty handy, right? This way we can quickly find the tech debt in the project and use the severity to decide whether to fix each item.

But before you start, you absolutely have to make sure your tests are all passing right now (all green). Otherwise you'll have no way to tell whether something was already broken or whether you just broke it!

The four kinds of debt AI racks up most

I want to pull one thing out here and look back at that prompt, because I specifically called out four things in it:

  • Duplicated logic: The same feature or task written two or more times.
  • Oversized components: One file crammed with too many jobs, more than N lines.
  • Inconsistent patterns: The same thing written different ways in different places.
  • Docs that don't match the code: CLAUDE.md, SPEC.md, and the code saying different things.

So why call out these four in particular? Because they're the debts AI racks up most often.

The root cause still comes back to the Context thing we keep talking about. Every time you use the AI, it's actually starting from zero. Unless you've written this stuff into specific files and use CLAUDE.md or SPEC.md to point the AI at them, it has no idea how your earlier code was written.

That's a lot of stuff. Pay it all back at once?

Honestly, no. But you can't ignore it either.

You should pick out the items with the biggest impact first, fix those, and keep updating step by step, instead of trying to do it all in one go.

Of course, there's one thing I still need to stress here:

The high, medium, and low the AI gives you are just its opinion, not gospel. You're the owner of this project, so you decide which debts to pay off first.

If you're not sure, think back to what we said about the MVP in earlier days: get the most important features right first and take your time with the rest. For an expense tracker, the core thing is that the "calculations" can never be wrong. Anything else can wait, as long as it doesn't get in the way of using the app.

And since that's a Plan Mode result, don't forget to have the AI save it. You can type:

Text
Please save that tech debt list in full as docs/TODO.md, keeping the severity and recommendation for each item. Don't work on any of them yet.

After that, just take your time reading through TODO.md.

Let's try paying off some debt

Now let's actually pay off some tech debt. In my case, one of the items the AI found was that the formatting Hook we set up on Day 22 has no Prettier config file. So it's been formatting everything with Prettier's own defaults (double quotes, semicolons), while the project's existing code uses single quotes and no semicolons.

That means every time the AI changes a file from now on, that file gets formatted in a different style. That's exactly the inconsistent patterns we just talked about, and it counts as tech debt too. On top of that, the src/hook-test.js we used back then to test the Hook is still sitting in the project.

This one's relatively small, so there's no real need to open Plan Mode for it. Just ask the AI to do it in Accept Edits Mode.

Text
Please add a Prettier config file, .prettierrc. Base the rules on the style of the project's existing code (quotes, semicolons, line width). Don't use Prettier's defaults.

Once it's added, run npx prettier --check src once to confirm that almost none of the existing files need to change. While you're at it, delete src/hook-test.js, which was left over from testing the Hook earlier.

When you're done, run npm test once, and mark the "No Prettier config file" item in docs/TODO.md as done.
Note

.prettierrc is Prettier's config file. You can set your code formatting rules in it, like whether to use single or double quotes, whether to add semicolons, the max line length, and so on.

Notice I didn't tell it whether to use single or double quotes. I asked it to go look at the existing code style on its own.

The conversation asking the AI to add .prettierrc and delete hook-test.js

Review: with refactoring, you're checking that nothing changed

Finally, say you're done refactoring. You absolutely need to have the AI run these:

  • npm test: Confirms the money-calculation logic wasn't touched. All those tests you spent time writing on Day 23 become your safety net today.
  • npm run build: Confirms the project still builds and runs, since a refactor can move a lot of files around.
  • Click through the screens yourself: You could use some automated testing tools to check the screens, but we're mainly reviewing whether the features are correct, so this layer is all on you.

Running them is easy too. Just give it this prompt:

Text
Please run the following commands and report the results back to me:

1. npm test
2. npm run build

After the refactor, npm test still passes everything

I'll leave the rest for you to try refactoring on your own.

How often should you take inventory?

I don't think there's really a standard answer here. You can decide how often based on the project's size, complexity, and how far along it is.

For example... with our expense tracker app, from the day we started until now, we never took inventory once. And today the first inventory turned up 30 items. That's not a huge number, but I'd still recommend dealing with it early.

So if I had to give you a rule, instead of counting by "how often," I'd suggest going by "timing." Take inventory whenever you hit one of these moments:

  • After a big redesign: Like when we reworked the screens in earlier days. That's a good time to tidy up while you're at it.
  • When the AI starts acting weird: Like fixing A breaks B, or it writes another copy of something that already exists.
  • Before launch: No matter what, I'd recommend checking at this point, since real users are going to be using it.

Wrapping up

We're about at the end, so here's a quick recap:

  • Tech debt isn't a bug. It's something that doesn't hurt now but will hurt later. The AI only looks at one task at a time, so going back to clean up is something you have to kick off.
  • The four debts AI racks up most: duplicated logic, oversized components, inconsistent patterns, and docs that don't match the code.
  • Take inventory in Plan Mode, save the list in the project, and pay off the biggest-impact items first. Just do the small stuff directly; anything that needs real surgery goes through Plan Mode, one item at a time.
  • With refactoring, you're checking that nothing changed. Only commit once tests, build, and the screens all pass. If something fails, roll straight back instead of forcing a fix.

The debt's been inventoried and the tests are all green, so tomorrow we're deploying the app and giving it a real public URL.

Hope this post helped you pay off your debt. See you tomorrow!
